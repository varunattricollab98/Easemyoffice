# Admin single-day entry and bulk back-fill for attendance — follow-up (v2)

Follow-up commit `b845dec` addresses the four issues raised in v1: the bulk loop's per-row write is now isolated, both admin actions re-check the employee's joining date server-side, `invalidateAttendance` was broadened to cover the employee-facing caches, and `tagEntrySource` now inspects the update error. All four are genuinely resolved on inspection. The shared `attendance-rules.ts` pair is still byte-identical and the validator was untouched, so the v1 scoring guarantees carry over unchanged.

Watch for: making `writeManualAttendance` throw on DB error (the mechanism that makes the bulk per-row catch meaningful) also changes the **missed-login regularization** path's error surface — previously a DB write failure there was silently swallowed and the request returned 200 OK; it now propagates to the top-level 500 handler (confirmed). This is a net improvement (silent data loss → loud failure) but it is a real behavioral change, not "exactly as before," and it leaves the `attendance_requests` row already marked approved when the 500 fires. No other regressions found.

**Verdict**: APPROVED

## High-level view

Issue 1 (bulk batch abort) is fixed correctly: each `writeManualAttendance` in the bulk loop is wrapped in try/catch and records a failed per-row result, and `writeManualAttendance` now checks its insert/update error objects and throws, so the catch actually fires on a DB fault instead of the error being swallowed. The joining-date re-check (Issue 3) runs before the write in the bulk path, so a before-joining row is reported as a failed result rather than written.

Issue 3 (no server-side joining-date check) is fixed symmetrically in both actions: `joining_date` is now selected and the actions reject `work_date < joining_date` with a plain ISO string compare. That is the exact complement of the client's `joining_date <= date` picker filter, and a null `joining_date` falls through to "allowed," matching prior behavior for employees without a recorded join date.

Issue 2 (invalidation narrower than its comment) is fixed by invalidating `hrms-attendance-events`, `my-attendance-current`, `my-attendance-month`, and `my-attendance-events`. The live keys are parameterized (`["my-attendance-current", employeeId]`, `["my-attendance-month", employeeId, from]`, `["hrms-attendance-events", outcome]`), but TanStack Query invalidates by key prefix, so the prefix-only keys used here do match the parameterized queries. The comment now matches the code.

Issue 4 (silent provenance tag failure) is fixed: `tagEntrySource` inspects the update error, treats an un-migrated missing-column error as the expected no-op, logs any other error, and still never throws, so a failed tag can no longer abort the write path and a genuine failure on a migrated DB is no longer invisible.

### Bulk per-row isolation now reaches the write

The v1 gap was that the bulk loop guarded validation and employee lookup but awaited the write bare, so a write-time DB error escaped the loop and 500'd the batch. Two coordinated changes close this. `writeManualAttendance` now checks both branches:

```ts
if (existing) {
  const { error } = await db.from("attendance").update(patch).eq("id", existing.id);
  if (error) throw new Error(error.message);
} else {
  const { error } = await db.from("attendance").insert({ … });
  if (error) throw new Error(error.message);
}
```

and the bulk call site wraps it, pushing `{ ok: false, message }` on catch and `continue`-equivalent flow. The accumulated `results` survive and the loop finishes, so a single CHECK violation or transient fault now degrades to one failed row in the response envelope (`{ ok: true, results, written, failed }`) instead of aborting everything. This restores the "one bad row never aborts the batch" guarantee the design promised.

### Joining-date re-check is server-side and symmetric

Both actions now select `joining_date` and gate on it before writing:

```ts
if (employee.joining_date && check.normalized.work_date < employee.joining_date) {
  // single-day: return fail("That date is before the employee's joining date.");
  // bulk: push a failed result and continue
}
```

`check.normalized.work_date` and `joining_date` are both `YYYY-MM-DD`, so the lexical `<` is a correct date comparison. The single-day path returns a 400 `fail`, the bulk path records a failed row — the right shapes for each surface. The back-date window (`MANUAL_ATTENDANCE_BACKDATE_DAYS`) still caps absolute reach; this adds the per-employee tenure floor that was missing. A null `joining_date` is treated as "no floor," which is the same permissive stance the client picker takes.

### Invalidation now matches its comment, and prefix matching makes it effective

The broadened `invalidateAttendance` adds the four previously-missing keys. Worth confirming because the live queries are parameterized while the invalidation keys are prefix-only — e.g. the query is `["my-attendance-current", employee.id]` but the invalidation passes `["my-attendance-current"]`. TanStack Query's default `invalidateQueries` matching is by key prefix, so the shorter key matches every per-employee instance; the employee-facing My Attendance screen and the HRMS daily-events list (`["hrms-attendance-events", outcome]`) are now actually refreshed after an admin write.

### Provenance tagging distinguishes "column absent" from real failures

`tagEntrySource` now reads the update's `error` object. A missing-column error on an un-migrated DB (matched on the message mentioning `entry_source` plus a column/schema-cache phrase) stays a deliberate no-op; any other error is `console.error`-logged; a defensive outer catch logs an unexpected throw. It still never throws, so provenance remains best-effort and can never abort the already-completed row write. The asymmetry v1 flagged — a genuine tag failure on a migrated DB being invisible — is gone.

### Ripple onto the missed-login path

The same `if (error) throw` that makes the bulk catch meaningful also fires on the shared `writeManualAttendance` used by `regularizeDay`, which the `missed_login_regularization` approval branch calls without a try/catch. At the base (`1aa9964`) the original `regularizeDay` ran its update/insert without checking the error, so a DB write failure there was silently swallowed and the handler returned 200. Now that failure throws, unwinds past the unguarded call, and hits the top-level `catch` that returns 500 with the message. Because the `attendance_requests` row is set to `approved` earlier in the same handler, a 500 at this point yields an approved request whose attendance row was not written — a partial outcome the caller sees as an error rather than a false success. This is strictly more honest than the old silent swallow, so it is not a defect, but the briefing's framing that the path behaves "exactly as before" is only true for the success case; the DB-error case changed from 200-with-silent-loss to 500. The single-day `admin_set_attendance` path shares this 500-on-DB-error surface, but that action is new in this task, so there is no prior behavior to regress against.

### Unchanged guarantees spot-checked

The two `attendance-rules.ts` copies are byte-identical (same checksum) and the follow-up touched only `hr-requests/index.ts` and `hrms/attendance.tsx`, so the validator, the `regularizedAttendance` scoring, the login-only open-row shape, the IST `istInstant`/`istParts` handling, and the off-day crediting are all untouched from v1. Admin gating remains the server-side `user_roles` check returning 403 for non-admins on both actions.
