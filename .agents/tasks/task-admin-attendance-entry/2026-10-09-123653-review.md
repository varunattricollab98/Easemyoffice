# Admin single-day entry and bulk back-fill for attendance (v1)

Adds an admin-only path to create or correct past attendance days so the owner can seed the current month (e.g. the 1st–11th) from WhatsApp login/logout timings before the portal goes live on the 12th. There are two front doors — a single-day "Add / edit attendance" dialog and a one-employee-across-a-range bulk grid — but both funnel through one new admin-gated action pair in the `hr-requests` edge function, and both reuse the existing `regularizedAttendance` scoring helper so a hand-entered day is byte-for-byte indistinguishable from a real punch in every downstream read (payroll, My Attendance, command center, month views). The refactor extracts the row-writing core (`writeManualAttendance`) out of the old `regularizeDay` and shares a new pure validator (`validateManualAttendanceEntry`) across both the single and bulk actions. The schema change (an `entry_source` tag) is optional, idempotent, and owner-applied, and the write path degrades to a correct row when the column is absent.

Watch for: the bulk loop's per-row **write** is not wrapped in try/catch (confirmed) — one DB-level failure aborts the whole batch via the top-level 500 handler, contradicting the "one bad row never aborts the batch" guarantee, which only holds for *validation* failures. Also, the client's `invalidateAttendance` comment claims it refreshes My Attendance and the command center, but it only invalidates the two `hrms-attendance-*` keys (likely); those employee-facing views use `my-attendance-*` keys and are not touched. Admin gating itself is correctly server-side.

**Verdict**: NEEDS_CHANGES

## High-level view

The design keeps a single scoring path: the body of the old missed-login `regularizeDay` is pulled into `writeManualAttendance`, which both admin actions and the existing regularization path now call. That is why an admin-entered login+logout scores identically (worked/window/late/status/overtime) to a punch, and why off-days credit as overtime with window 0 instead of fabricating required hours. `regularizeDay` is preserved as a thin wrapper, so the missed-login approval path's observable behavior is unchanged.

Admin authority is decided only on the server: both `admin_set_attendance` and `admin_bulk_set_attendance` 403 when the caller is not an admin in `user_roles`, and the client's "active employees" filtering is never a trust boundary. One gap at that boundary: the server does not re-check that the chosen employee had actually joined by the entered date, so a crafted request can write attendance for a date before an employee's joining date.

A login-only entry writes an open `in_progress` row mirroring `attendance-punch`'s open insert (no fabricated hours); a login+logout entry is fully scored.

The `entry_source` tag is best-effort: the row is written first without it, then a follow-up update tags provenance, and on an un-migrated DB the tag silently no-ops. But provenance is write-and-forget — a failed tag update is invisible even on a migrated DB.

Resilience in the bulk path is only half-built. Validation and employee-lookup failures are captured per row and reported, but the actual write is awaited bare, so a write-time error escapes the loop and 500s the batch.

<summary>Issues (4)</summary>

1. **Bulk write not isolated per row** — `writeManualAttendance` inside the bulk loop is awaited without try/catch, so a single write-time failure (CHECK violation, transient DB error) throws out of the loop and the top-level handler returns 500, aborting the whole batch and losing the per-row results already accumulated. Wrap each write in try/catch and record a failed result instead.
2. **Invalidation scope narrower than its comment** — `invalidateAttendance` only invalidates `hrms-attendance-month` and `hrms-attendance-day`; My Attendance (`my-attendance-*`) and the daily-events (`hrms-attendance-events`) caches are not refreshed. Either broaden the invalidation or correct the comment so it does not overstate coverage.
3. **No server-side joining-date check** — the single-day and bulk actions trust any existing `employee_id` and never re-apply the client's "joined by this date" filter, so attendance can be written for a date before the employee joined. Re-validate joining date server-side.
4. **Silent provenance-tag failure** — `tagEntrySource` ignores the update result entirely (not just the missing-column case), so on a migrated DB a genuinely failed tag write leaves an untagged admin row with no signal. Distinguish "column absent" from other errors, or at least log the latter.

<summary>Details</summary>

### One scoring path for punches, regularization, and admin entry

`writeManualAttendance` is extracted from the old `regularizeDay`, which now delegates to it while keeping its original guard (needs both login and logout, otherwise skip) so the missed-login approval path behaves exactly as before.

```
admin_set_attendance ─┐
admin_bulk_set_attendance ─┤→ writeManualAttendance → regularizedAttendance (login+logout)
regularizeDay (missed-login) ─┘                      └ open-row shape (login-only)
```

The login+logout branch copies the exact field set the regularization path wrote (`first_login_at`, `last_logout_at`, `open_since: null`, worked/window/late/status/overtime plus the schedule snapshot), so a scored admin day is identical to a scored punch day. The login-only branch writes an `in_progress` row field-for-field like `attendance-punch`'s open insert (`first_login_at`/`open_since`/`last_activity_at` at the login instant, `last_logout_at: null`, worked/window/overtime 0, `is_late`/`late_minutes` from `lateMinutes`); the punch insert additionally carries office/geo columns, legitimately absent for a hand-entered day. These field lists are what make downstream reads (payroll via `hrms-attendance-month`, month grid, command center) correct without any of them knowing the row was hand-entered.

### Admin gating and the joining-date gap

Both actions 403 when `isAdmin` — derived from `user_roles` read through the service-role client against the authenticated user — is false; the client cannot assert its own admin status.

The soft spot is scope within that boundary. `useActiveEmployees` hides resigned/terminated staff and anyone not yet joined by the target date, but the server only checks that the `employee_id` resolves to an existing employee — it does not re-apply the joining-date rule. A crafted request can therefore write a day that precedes an employee's joining date, which would then score and feed payroll. The back-date window (`MANUAL_ATTENDANCE_BACKDATE_DAYS = 45`) caps how far back any day can go but says nothing about per-employee tenure.

### Bulk resilience is only partial

The bulk loop is defensive about *input*: a blank login is a deliberate skip, a missing/unresolved employee is a failed row, and `validateManualAttendanceEntry` failures are captured with their message — each `continue`s without touching the batch. The gap is the write itself:

```ts
await writeManualAttendance(db, { … entrySource: "admin_bulk" });
results.push({ index, employee_id: employeeId, work_date: check.normalized.work_date, ok: true });
```

There is no try/catch around this call. `writeManualAttendance` performs real DB operations (a select, then an insert or update), none of whose errors are checked, and any thrown error propagates to the top-level `Deno.serve` handler, which returns 500. That discards the `results` collected so far and aborts the remaining rows — exactly the "one bad row aborts the batch" outcome the design set out to prevent. The per-row safety currently holds only for validation and lookup, not for persistence. Wrapping the write and pushing a failed result on error would close the gap.

### entry_source is write-and-forget

`tagEntrySource` writes the row without `entry_source`, then issues a follow-up `update` to tag it, inside a try/catch justified as tolerating the missing column on an un-migrated DB. But Supabase surfaces a missing-column error on the result object rather than throwing, and the code never inspects that error — so the no-op works, but not via the try/catch the comment credits. Because the error is never inspected, a genuine tag failure on a *migrated* DB (constraint, transient fault) is equally invisible: the admin row persists untagged with no signal. Nothing reads `entry_source` yet, so the blast radius today is auditability, but the asymmetry is worth tightening if provenance is meant to be trustworthy.

### Client invalidation overstates its reach

`invalidateAttendance` invalidates `hrms-attendance-month` and `hrms-attendance-day`, and its comment claims this covers "the Monthly grid, per-employee calendar, Today tab, My Attendance, payroll and the command center." Payroll does read `hrms-attendance-month`, but My Attendance uses `my-attendance-month`/`my-attendance-current`/`my-attendance-events` and the HRMS daily events use `hrms-attendance-events` — none of which are invalidated. These resolve on next navigation/refetch, so this is staleness and comment accuracy rather than a correctness bug, but the comment claims coverage the code does not provide.

### IST and date handling

Instants are built with the fixed `+05:30` helper (`istInstant`) and `today` is derived server-side from `istParts(new Date()).date`, so neither the window scoring nor the back-date check drifts with the server's zone. The client `dateRange` steps a UTC-midnight cursor over date-only strings and reads them back with `timeZone: "UTC"`, avoiding the `new Date(iso)` local-zone trap on date-only strings.

### Test coverage

Covered: the two new scoring cases (flexible full day; off-day overtime) assert concrete minute values through the real `regularizedAttendance`, so a reverted scoring change would fail; the validator's full edge matrix; and the byte-identical shared-copy guard. Typecheck is clean and all 285 tests pass locally.

Not tested: the edge function's new actions have no integration-level coverage, so the two behavioral gaps above live in untested code — specifically the bulk loop's batch-abort-on-write-error and the server-side absence of a joining-date check. There is also no test that a login-only admin row matches the punch open-row shape, though the field lists line up on inspection.

### Not reviewed / out of scope

The migration is additive and idempotent and does not alter the status CHECK; it is owner-applied by this repo's convention. The `allowAnyDay` prop on `MonthCalendar` and the `attendance` addition to the `AuditEntity` union are small, correctly-defaulted additions that leave existing callers unchanged. No unrelated changes are bundled in the diff.
