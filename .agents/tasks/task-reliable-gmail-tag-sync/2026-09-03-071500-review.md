# Server-side scheduled Gmail tag sync for reliable lead capture (v1)

The inbox previously turned "<Name> lead"-tagged Gmail threads into CRM leads only from the client: admin-only, one 25-email inbox page, and with a dedup key that disagreed with how leads were actually created — so most tagged emails never reached the sales person's lead list. This change makes a server-side pg_cron edge function (`gmail-tag-sync`) the authoritative path: it enumerates the full mailbox through a new Apps Script `tagged` action, matches each owner tag to a profile with a shared three-tier rule, dedups on the same `[realEmail, senderAddr]` key the client uses, and inserts leads via the service-role client regardless of who is logged in. The client effect is demoted to a best-effort accelerator, and unmatched owner tags are now surfaced (toast + amber note) and logged to `email_log` instead of being dropped.

**Watch for:** the full-mailbox guarantee is capped at 500 threads per run by the function's `MAX_PAGES` safety cap, and Apps Script's `label.getThreads()` returns at most 500 threads per label with no pagination — both silently drop coverage above those limits (confirmed), which is the one thing that can still make "every tagged email" false. The `email_log` `status='unmatched'` insert only works if the operator has run `ADD_GMAIL_TAG_SYNC_CRON.sql` to widen the CHECK constraint first, and the function swallows that failure (confirmed). Dedup, NOT NULL satisfaction, and the shared parsing helpers are all verified consistent.

**Verdict**: NEEDS_CHANGES

## High-level view

The reliability guarantee moves from the browser to a pg_cron-driven edge function that runs every 10 minutes independent of any logged-in user, using the service role to bypass RLS — coverage no longer depends on an admin having the inbox open. The remaining gap is scale: the run stops at 500 threads (`MAX_PAGES × PAGE_SIZE`), and the Apps Script label enumeration is itself capped at 500 threads per label, so a mailbox with a large tagged backlog will not fully reflect in the CRM — directly contradicting the "every email" requirement for large accounts.

Duplicate prevention is solid: the seven pure helpers in `_shared/gmail-parse.ts` are byte-identical to `src/lib/gmail.ts` (verified function-by-function), the `[realEmail, senderAddr]` key is computed identically on both sides, and the server maintains an in-run map so two threads sharing one customer don't double-insert within a pass. One asymmetry survives on both sides: the persisted dedup map only holds the real `email` column, so the `senderAddr` half only dedups within a run, not against prior runs.

Unmatched owner tags are logged to `email_log` with `to_email=""` and `status='unmatched'`, which requires the cron SQL's CHECK-constraint widening to have been applied first; the insert is best-effort and its failure is swallowed, so a mis-ordered deploy loses the unmatched audit trail silently. The client insert-scoping avoids RLS denials for sales/bd/admin but not for a user whose only roles are documentation/accounts/renewals.

<summary>Issues (6)</summary>

1. **500-thread run cap** — `MAX_PAGES=20 × PAGE_SIZE=25` stops the sync at 500 threads per run with no carry-over cursor, so a backlog larger than 500 never fully syncs. Raise the cap, persist a high-water mark, or process oldest-unsynced-first; at minimum log when the cap is hit.
2. **Apps Script `getThreads()` per-label cap** — `label.getThreads()` with no args returns at most 500 threads for a single label, silently truncating any label with more tagged threads. Use the paginated `getThreads(start, max)` overload per label instead of slicing an already-truncated array.
3. **email_log CHECK depends on deploy order** — the `status='unmatched'` insert fails (silently, in a swallowed try/catch) unless `ADD_GMAIL_TAG_SYNC_CRON.sql` widened the constraint first. Document the ordering as required, and surface the swallowed error to the function response instead of dropping it.
4. **Per-page full re-enumeration in Apps Script** — `getTagged` re-lists every lead label and all their threads on every page call, an O(pages × mailbox) cost, and threads arriving mid-run can shift the offset window. Dedup absorbs the correctness risk but the rebuild is wasteful; build the ordered thread list once or accept single-page runs for typical volumes.
5. **created_by attribution differs client vs server** — client inserts set `created_by: user.id` (whoever's inbox is open) while the server sets `created_by: profile.id` (the owner). Not a duplicate risk, but audit and `created_by`-scoped RLS reads will attribute the same lead differently depending on which path won. Pick one convention.
6. **Client self-scope leaves some roles unable to insert** — non-admins only auto-create their own tags, but `leads_insert` RLS requires `sales`/`bd`/admin; a user with only documentation/accounts/renewals roles viewing their own tagged email would still hit a denial toast. Gate the client insert on the insert-capable roles, not just on ownership.

### Full-mailbox guarantee is capped at 500 threads

The function's own comment states the intent — "guarantees EVERY Gmail thread tagged ... across the FULL mailbox" — but two hard limits cap that at 500 threads per run (confirmed):

```
MAX_PAGES = 20
PAGE_SIZE = 25          // 20 * 25 = 500
```

The page loop breaks on `!result.hasMore` or when `page` reaches `MAX_PAGES`, and no cursor is persisted between runs — every invocation starts at `start=0`. So if more than 500 tagged threads exist and are not yet leads, the tail beyond 500 is never processed on any run, because each run re-scans the same first 500. For the reported situation (many emails already tagged, "only few reflecting") a large existing backlog is exactly the case that stays broken. Hitting `MAX_PAGES` also looks identical to a clean finish in the response.

Compounding this, the Apps Script side has its own ceiling. `leadLabels[li].getThreads()` is called with no arguments:

```javascript
var lt = leadLabels[li].getThreads(); // all threads for this label
```

The no-arg `GmailLabel.getThreads()` returns at most 500 threads. So `allThreads`/`total` is already truncated before the server ever paginates, and `hasMore` is computed against that truncated `total`. The paginated overload `getThreads(start, max)` should be used per label to actually walk the whole label.

Neither cap breaks dedup or creates duplicates; they cap *coverage*, the specific property the change set out to guarantee.

### Dedup consistency between client and server

The dedup key is computed identically on both sides:

```
// client (inbox.tsx resolveLeadFields) and server (gmail-tag-sync) both:
dedupKeys = [realEmail.trim().toLowerCase(), senderAddr].filter(Boolean)
```

`realEmail` and `senderAddr` are derived through the same helper chain (`parseFrom`, `isThrowawayAddress`, `parseWeb3FormLead`), and those helpers in `_shared/gmail-parse.ts` are byte-identical to `src/lib/gmail.ts` — verified function-by-function for all seven. Both sides seed their lookup map from `leads` filtered on `source='email'`, keyed by the lowercased `email` column, and treat a hit on any dedup key as "already a lead." The server also guards in-run duplication by writing pending keys into the map as it builds the batch, so a second thread for the same customer in the same pass skips.

One asymmetry to note: the persisted `leadByEmail` only ever contains the real `email` column value, never the sender/relay address, because that is all that is stored on the lead row. So the `senderAddr` half of the key only dedups *within a run*, not against previously-created leads. This matches on both sides, but it means a relay-only lead created in run N (real email empty, only relay address differing) can be re-created in run N+1 — worth confirming against real data.

### Client effect timing and unmatched-tag surfacing

The premature skip on `parseFrom(e.from).address` (the relay/sender address alone) is gone; the effect now defers the "already a lead?" decision entirely to `existingLeadFor([realEmail, senderAddr])` inside `syncTagged`, so a genuinely-new tagged email is no longer dropped by a key that disagreed with how the lead would be created. A `threadId` is added to `syncedRef` only after it is pushed to `pending`, and unmatched-tag threads are deliberately *not* added, so a later profile rename or label correction re-evaluates them on the next poll. Unmatched tags are aggregated by a sorted signature and toasted at most once per distinct set, so the 60s poll doesn't re-fire it.

### Client insert scope vs leads_insert RLS

FEAT-003 scopes non-admin client inserts to the current user's own tag (`if (!isAdmin && owner.id !== user?.id) continue`). The stated reason is avoiding RLS denials, but `leads_insert` is actually:

```sql
WITH CHECK ( is_admin(auth.uid()) OR has_role(auth.uid(),'sales') OR has_role(auth.uid(),'bd') )
```

There is no per-row `assigned_to = auth.uid()` constraint, so the self-scoping is a race-avoidance choice, not an RLS necessity. The gap is the inverse: a user whose roles are only `documentation`/`accounts`/`renewals` is *not* in the insert policy at all, so even self-scoped inserts for their own tagged email would be denied and produce an error toast. The scope check keys on ownership, not on whether the current user holds an insert-capable role.

### Auth and service-role posture

The function mirrors `process-reminders`: `CRON_SECRET` via `body.secret` or the `x-cron-secret` header, 401 when unset or mismatched, service-role client with `persistSession:false`, `verify_jwt=false` in `config.toml`. The cron SQL posts with the anon key in `Authorization` and the secret in the body, identical to `ADD_STALE_FOLLOWUP_CRON.sql`. It calls the Apps Script directly rather than through `gmail-bridge` to avoid an extra hop; the `gmail-bridge` `tagged` branch is still added and used by the client path. `GMAIL_TOKEN` is passed as a URL query parameter to the Apps Script (as the pre-existing inbox/thread actions already do), so this is not new exposure, but the token can land in Apps Script request logs — pre-existing, out of scope, noted for completeness.

### NOT NULL and email_log satisfaction

`leads.client_name` (NOT NULL) is satisfied by the fallback chain `parsed.name || fromName || realEmail || subject || "Email lead"`, which cannot be empty; `mobile` (NOT NULL) falls back to `""`; `email` is nullable and set to `realEmail || null`. All other inserted columns exist on the table.

The unmatched path writes `email_log` with `to_email: ""` (satisfies NOT NULL) and `status: "unmatched"`. That status is only legal after `ADD_GMAIL_TAG_SYNC_CRON.sql` widens the CHECK from `('sent','failed')` to include `'unmatched'`. The insert is wrapped in a try/catch that swallows the failure — so if the function is deployed before the SQL is run, every unmatched tag is lost from the audit trail with no signal. The ordering should be a documented hard prerequisite, and the swallowed error promoted into the response so a failed widening is visible.

### Test coverage

**Not tested:** there is no test framework in the repo and the sandbox is `INTEGRATIONS_ONLY`, so nothing here is covered by automated tests and TypeScript/React compilation could not be verified. Behaviors most in need of a manual/CI check before relying on the guarantee: pagination past 500 threads (currently can't be exercised because of the cap), the `email_log` unmatched insert against the widened constraint, non-admin client inserts under each role, and parity between `_shared/gmail-parse.ts` and `src/lib/gmail.ts` (a CI diff/hash check would prevent future drift, since the two files must be kept identical by hand).
