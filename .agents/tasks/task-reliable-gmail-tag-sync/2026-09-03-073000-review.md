# Full-mailbox coverage and attribution fixes for Gmail tag sync (v2)

This pass re-reviews the six issues from v1 after commit `e653898`. The coverage guarantee was the crux: the server run cap moved from 500 to 20,000 threads/run (`MAX_PAGES=200 × PAGE_SIZE=100`) with a `cap_hit` flag and an `email_log` breadcrumb when even that is exceeded, and the Apps Script now walks each lead label past Gmail's 500-per-call ceiling via `getAllThreadsForLabel`. Owner attribution was unified (`created_by` = matched owner on both paths), the swallowed `email_log` failure is now surfaced as `email_log_error`, and the client auto-sync is gated on a real insert-capable role. All six are genuinely fixed in the code as written, not just claimed.

**Watch for:** the only residual is the new Apps Script cache path (`buildTaggedThreadIndex`) — within a run it re-materializes threads from a cached id list via `getThreadById`, and if any id fails to resolve mid-run the list silently shrinks, shifting the server's `start/max` window past unseen threads (possible, low-probability since sync never removes labels). The 120s TTL is shorter than the 10-minute cron interval so cross-run staleness can't occur under normal timing (confirmed). Nothing here blocks shipping.

**Verdict**: APPROVED

## High-level view

Coverage is now real for realistic mailboxes. The server sweeps up to 20,000 tagged threads per run and, because already-created leads keep their label and are removed only by dedup, a single run is large enough to reach the tail of a backlog rather than re-scanning the same head forever. Hitting even the 20,000 ceiling is no longer disguised as a clean finish — `cap_hit:true` plus an `email_log` row make it visible. On the Apps Script side each lead label is walked completely by looping `getThreads(offset, 500)` until a short page, so labels over 500 threads are no longer truncated at the source.

Attribution is consistent across the two write paths: the client auto-sync now stamps `created_by = r.owner.id` to match the server's `created_by = profile.id`. This is RLS-safe — `leads_insert` checks only role membership (`is_admin OR sales OR bd`), with no per-row `created_by` or `assigned_to` predicate, so writing the owner's id rather than the actor's id cannot trip the policy. The three manual actions (claim/markMine/assign) deliberately keep `created_by = user.id` and are unchanged.

The client auto-sync is gated on `canInsertLeads = isAdmin || hasRole('sales') || hasRole('bd')`, drawn from the real `useAuth` (`hasRole` is `roles.includes(r)`), so documentation/accounts/renewals-only users no longer hit an RLS denial toast from the accelerator. Unmatched-tag surfacing runs before that gate, so those users still see amber unmatched notes; the authoritative server cron covers their tagged emails regardless.

The one new mechanism to keep an eye on is the Apps Script thread-index cache: it removes the O(pages × mailbox) re-enumeration cost by building the ordered id list once per run and caching it, but the cached read rebuilds `GmailThread` objects by id and drops any that no longer resolve, which can shrink the paginated list mid-run.

### Coverage: run cap and per-label walk both resolved

The server pages `start=0,100,200,…` up to `MAX_PAGES=200`, breaking on `!result.hasMore`. `capHit` is set only on the last permitted iteration (`page === MAX_PAGES - 1`) while Gmail still reports `hasMore` — the natural-finish path breaks earlier, so a clean sweep reports `cap_hit:false` and a truncated sweep reports `cap_hit:true`, backed by a best-effort `email_log` row ("Page cap hit"). That closes the v1 complaint that hitting the cap looked identical to finishing.

The Apps Script ceiling is closed at the source. `getAllThreadsForLabel` loops `label.getThreads(offset, 500)`, pushing each batch and advancing `offset` until a batch shorter than 500 (or empty) arrives:

```javascript
while (true) {
  var batch = label.getThreads(offset, GMAIL_GETTHREADS_MAX); // 500
  if (!batch || batch.length === 0) break;
  for (var i = 0; i < batch.length; i++) out.push(batch[i]);
  if (batch.length < GMAIL_GETTHREADS_MAX) break; // last short page
  offset += batch.length;
}
```

Termination is sound: every full page advances the offset by exactly the batch length, and the loop can only exit on a short/empty page. A label with 1,200 threads yields pages of 500/500/200 and stops. Combined with the 20,000/run server ceiling, a large already-tagged backlog now reflects into the CRM in one pass.

### Apps Script thread-index cache — the one new risk

`buildTaggedThreadIndex` builds the combined, de-duplicated ordered id list once and caches it for 120s so the server's page sequence within a single run doesn't re-enumerate the whole mailbox each page. The cache read path is where a new failure mode lives:

```javascript
if (cachedIds) {
  var ids = JSON.parse(cachedIds);
  var threads = [];
  for (var k = 0; k < ids.length; k++) {
    var th = GmailApp.getThreadById(ids[k]);
    if (th) threads.push(th);   // silently drops ids that no longer resolve
  }
  if (threads.length) return threads;
}
```

If any cached id fails to resolve on a later page (thread archived out of a label, deleted, or a transient `getThreadById` miss), that thread is dropped and `total = allThreads.length` shrinks. The server computes `hasMore = (start + max) < total` and slices `allThreads.slice(start, start+max)` against the shrunken list, so a thread that would have sat at the boundary can be skipped for that run. It self-heals next run (fresh enumeration), and the probability is low because the sync never removes labels — but it is a coverage hole introduced by the caching, worth a placeholder-on-null or payload-cache hardening if the guarantee must be exact. The over-limit fallback (id list > ~95KB → skip caching → full re-enumeration every page) is correct, just slower.

The TTL is 120s against a 10-minute cron cadence, so a stale snapshot cannot leak from one run into the next under normal scheduling; the cache only ever serves the run that populated it. (The code comment says the key is "an id-signature of the ordered list" but the key is the fixed string `"tagged_index_v1"` — cosmetic comment drift, no behavioral effect since one run owns the cache window.)

### Attribution, insert gate, and email_log — confirmed resolved

`leads_insert` is `WITH CHECK (is_admin(auth.uid()) OR has_role(auth.uid(),'sales') OR has_role(auth.uid(),'bd'))` — role membership only, no per-row `created_by`/`assigned_to` predicate (confirmed in migration `20260512095324` and `COMBINED_DATABASE_SETUP.sql`), so the client's switch to `created_by: r.owner.id` cannot cause a denial and matches the server. Claim/markMine/assign still write `created_by: user.id` and are untouched.

The insert gate is genuine: `hasRole` is `roles.includes(r)` over the `AppRole` union that includes `sales`/`bd`, and `if (!canInsertLeads) continue;` runs before the `!isAdmin && owner.id !== user?.id` self-scope check — but `unmatchedTags.push(ownerTag)` runs before the gate, so surfacing is preserved for all roles, with `canInsertLeads` added to the effect deps.

The unmatched-tag audit insert captures its error into `emailLogError` and returns it as `email_log_error` (the same field also carries a failed `cap_hit` log insert), and `GMAIL_TAG_SYNC_SETUP.md` documents running the CHECK-widening SQL (step 2) before deploying the function (step 3).

### Test coverage

**Not tested:** the sandbox is `INTEGRATIONS_ONLY` with no test framework, so none of this is exercised by automated tests and no TypeScript/Deno compilation was run. The behaviors most worth a manual check before trusting the guarantee at scale: the Apps Script cache-rehydration path when a cached id fails to resolve mid-run (the one new risk above), a real over-500 label walk, and the `email_log` unmatched insert against the widened CHECK. Parity between `_shared/gmail-parse.ts` and `src/lib/gmail.ts` remains a hand-maintained invariant with no CI guard.
