# Documentation analytics dashboard with escalation system

This change restructures the documentation page from a flat task table into a role-aware tabbed interface. Admins get an analytics dashboard (per-person performance, bottleneck detection, escalated tasks), a tasks table with manual escalation, and a settings tab for configuring the escalation threshold. Documentation-role users see personal stats and their own tasks. The schema adds three columns (`escalated`, `escalation_reason`, `escalated_at`) to `documentation_tasks` with RLS policies. Escalation detection is hybrid: tasks can be manually flagged by admin, or auto-detected client-side when `updated_at` exceeds a configurable threshold (default 3 days).

Watch for: RLS policy conflicts with existing policies on `documentation_tasks` (confirmed), `updated_at` used as completion-time proxy gives skewed metrics when admins edit completed tasks (likely), and the escalation threshold query fires independently in three components rather than being shared (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The page restructure cleanly separates concerns by role using a straightforward conditional at the top of `DocumentationPage`. The admin gets three tabs, the doc person gets two, everyone else sees the bare task table. Each tab is its own component with its own data fetching, which keeps them independent but introduces redundancy in the threshold query.

The analytics approach is entirely client-side: all tasks for the period are fetched, then completion rates, average days, bottleneck stages, and escalation status are derived from that in-memory dataset. This works for small teams but the per-person `avgDays` calculation does a nested filter-then-reduce inside a loop over the person map, creating an O(n²) pattern that will degrade if task volume grows.

The escalation model is split-brained: manual escalation writes `escalated=true` to the database, but auto-detection is ephemeral client-side logic. This means the Analytics tab, the Tasks tab, and any external system querying `documentation_tasks` will disagree about which tasks are escalated. The design is intentional (avoids background jobs), but reviewers should understand this asymmetry.

The SQL migration adds columns and new RLS policies, but existing policies on `documentation_tasks` for UPDATE and SELECT operations may conflict or produce unexpected additive behavior when Supabase evaluates them with OR semantics.

<summary>Issues (5)</summary>

1. **RLS policy conflict risk** — The migration creates new UPDATE and SELECT policies without checking or dropping existing ones. If `documentation_tasks` already has policies for these operations, they combine with OR, potentially granting broader access than intended. Audit existing policies and either drop-and-recreate or make the new ones additive by design.
2. **Escalation threshold fetched three times** — `AnalyticsTab`, `TasksTab`, and the standalone tasks view each fire their own `useQuery` for `doc_escalation_days` with the same query key. While React Query deduplicates in-flight requests, the repeated boilerplate means any key typo silently breaks a tab. Lift the threshold fetch into a shared hook or pass it as a prop from the parent.
3. **`updated_at` as completion-time proxy** — Average days to complete is calculated as `differenceInDays(updated_at, created_at)`. Any post-completion edit (stage correction, notes update) inflates this metric silently. Consider using `escalated_at`-style explicit timestamp, or at minimum document the assumption.
4. **Split-brain escalation** — Auto-escalated tasks are only flagged in the browser. A task that's been stuck for 10 days shows as escalated to whoever is looking at the page, but the database field remains `false`. Any reporting, export, or notification system querying the DB directly will miss these. Acceptable as a V1 trade-off if documented; problematic if downstream consumers expect the DB to be the source of truth.
5. **`useMemo` with side effect for state sync** — `SettingsTab` uses `useMemo` to call `setDays` when `currentDays` loads. This is a side effect inside a memo and triggers a warning in React strict mode. Replace with `useEffect` or initialize state from the query's data directly.

## RLS policy layering on `documentation_tasks`

The migration at `setup/ADD_DOC_ESCALATION.sql` adds two new policies: `admin_can_update_escalation` (FOR UPDATE) and `assigned_user_can_read_own_tasks` (FOR SELECT). Supabase evaluates multiple policies on the same table and operation with OR semantics — if *any* policy passes, access is granted.

If the table already has an UPDATE policy (even one scoped to stage changes), the new admin update policy now grants admins full-row UPDATE capability, not just escalation fields. The policy's USING/WITH CHECK only verifies "is admin", without restricting which columns can be written. An admin could theoretically update `assigned_to` or `stage` through the escalation code path without the UI intending it.

Similarly, the SELECT policy grants access to `assigned_to = auth.uid() OR is_admin`. If a broader SELECT policy already exists (e.g., one that lets all authenticated users read tasks), this new policy is redundant. If a narrower one exists, the OR combination widens access. The migration should be preceded by a `DROP POLICY IF EXISTS` for any overlapping policies, or the new policies should be named to replace existing ones.

**Confidence: confirmed** — the SQL is explicit and Supabase's OR-semantics for same-operation policies is documented behavior.

## Escalation detection asymmetry

The code defines `isAutoEscalated` in `TasksTab` and repeats the same logic in `AnalyticsTab`'s `escalatedTasks` memo:

```typescript
// TasksTab
const isAutoEscalated = (task: DocTaskRow): boolean => {
  if (task.stage === "completed") return false;
  const daysSinceUpdate = differenceInDays(new Date(), new Date(task.updated_at));
  return daysSinceUpdate > escalationDays;
};

// AnalyticsTab (inline in useMemo)
if (t.stage !== "completed") {
  const daysSinceUpdate = differenceInDays(now, new Date(t.updated_at));
  return daysSinceUpdate > escalationDays;
}
```

Both instantiate `new Date()` at render time, which means the set of "auto-escalated" tasks can change between renders if the component re-renders around midnight. More importantly, the `AnalyticsTab` counts auto-escalated tasks in `totalEscalated` and the bottleneck stages, but only `TasksTab` offers the manual escalation button. If an admin sees a task as escalated in Analytics and switches to Tasks, the same task might not be highlighted if the period filter differs between tabs (Analytics uses its own period state, Tasks uses its own).

**Confidence: confirmed** — both tabs maintain independent `period` state.

## `updated_at` as completion timestamp

Average completion time uses `differenceInDays(new Date(t.updated_at), new Date(t.created_at))` for tasks where `stage === "completed"`. This relies on `updated_at` being set exactly when the task transitions to "completed". If `updated_at` is a database trigger that fires on any row modification (common in Supabase with `moddatetime`), any subsequent edit to a completed task — adding a note, correcting the stage, escalating — will silently inflate the average. The metric becomes unreliable over time.

The per-person table also uses this same calculation for its `avgDays` column, and it iterates `tasks.filter(...)` inside a `for...of` loop over the person map entries. For N tasks and M people, this is O(N×M) in the worst case. Fine for dozens of tasks, noticeable for thousands.

**Confidence: likely** — whether `updated_at` auto-fires on edits depends on the Supabase table configuration, which isn't visible in this diff. The O(N×M) pattern is confirmed.

## State sync via `useMemo` in `SettingsTab`

```typescript
useMemo(() => {
  if (currentDays !== undefined && days === "") {
    setDays(String(currentDays));
  }
}, [currentDays]);
```

`useMemo` is for deriving values, not for side effects. Calling `setDays` inside a memo is a React anti-pattern — it works in practice but triggers warnings under `<StrictMode>` and may break under concurrent features. This should be a `useEffect`, or better, initialize the input from `currentDays` directly and treat the query data as the source of truth until the user edits.

**Confidence: confirmed** — the code is in the diff at SettingsTab around line 800.

## Duplicated threshold fetching

The escalation threshold (`doc_escalation_days`) is fetched via `useQuery` with key `["doc-escalation-days"]` in three places: `AnalyticsTab`, `TasksTab` (which is rendered inside both admin and doc person views), and `SettingsTab` (uses key `["doc-escalation-days-setting"]` — a different key despite being the same data). React Query will deduplicate concurrent requests sharing the same key, but `SettingsTab` uses a distinct key, so a cache invalidation of one won't propagate to the other unless both are explicitly invalidated (which the save mutation does correctly). The risk is maintenance: a future developer adding a fourth consumer may use yet another key variant, and the UI would show stale threshold values.

**Confidence: confirmed** — the query keys are visible in the diff.
