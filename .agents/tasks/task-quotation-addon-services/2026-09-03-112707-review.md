# Rep-entered add-on services in the quotation email

Reps often bundle extra services (CA Services, Signage Board, etc.) with a quote, and until now there was no way to put them into the emailed quotation. This change adds an optional "Add-on Services" section to the Send Quotation dialog: a repeatable Service-Name + Amount row set with per-row removal and an "Add more service" button, and a matching email-safe table rendered into the quotation HTML between the pricing table and the multi-year discount block. Add-ons are flat amounts with no GST, filtered so only rows with a real name and a positive amount ever render, and the whole feature is additive email-content with no DB or schema change. The work touches a single file and builds on top of the existing multi-state / price-override / row-removal logic.

Watch for: the rep-typed add-on `name` is interpolated raw into the email HTML with no escaping, so a `<` or `&` in a service name produces malformed markup (possible; matches the file's pre-existing convention but the add-on name is the most free-form input yet). Amount is stored as a string and parsed with `Number()`, which silently drops non-numeric or non-positive rows rather than warning the rep (confirmed).

**Verdict**: APPROVED

## High-level view

The feature is wired through the existing `buildQuotationHtml` builder rather than bolted on: an optional `addons` param defaults to `[]`, and the section string is empty when there are no add-ons, so the email is byte-identical to before when the rep enters nothing. Reset-on-open, the immutable handlers, and the `emailHtml` dependency array follow the same patterns the surrounding price-override and removed-row state already use.

The parse-and-filter step lives in the `emailHtml` memo, not in the input handlers: the rep types freely, and only at render time are names trimmed and amounts coerced, keeping only rows with a non-empty name and a finite amount greater than zero. The trade-off is that a fat-fingered amount (e.g. `12x`) or a zero simply vanishes from the quote with no feedback.

The one latent gap is HTML escaping of the service name, which the whole file already skips for client name and plan fields, so this is a pre-existing convention the new code inherits rather than introduces.

### Add-on rendering routed through buildQuotationHtml

The section is produced inside `buildQuotationHtml` from a new optional `addons?: { name: string; amount: number }[]` param destructured with a default of `[]`. When the array is empty the builder returns an empty string and interpolates it as `${addonsSection}`, so there is no code path where an empty add-on list changes existing email output. The subtotal row sums `a.amount` across the already-filtered list, so it matches the rows rendered above it.

The section is interpolated exactly once, immediately after the `</td></tr>` that closes the pricing/notes block (the "first-come, first-served" note) and before the `<!-- MULTI-YEAR DISCOUNT -->` comment, as required. Markup is inline-styled and table-based, striped via `idx % 2`, with a navy `#0A1F4D` header and `#FFE39A` header cells mirroring the existing pricing table.

### Parse-and-filter at render time, string-backed input

`addonServices` holds `{ name: string; amount: string }[]`; the amount stays a string so the number input stays controlled without fighting the user mid-type. The `emailHtml` memo does the coercion:

```ts
const parsedAddons = addonServices
  .map((row) => ({ name: row.name.trim(), amount: Number(row.amount) }))
  .filter((row) => row.name !== "" && Number.isFinite(row.amount) && row.amount > 0);
```

`Number("")` is `0` and `Number("12x")` is `NaN`, both correctly excluded by the `Number.isFinite && > 0` guard. The parsed shape `{ name: string; amount: number }` matches the builder's param type. Duplicate names each render as their own row and add to the subtotal, which is correct for a rep listing two distinct services with a shared label.

The behavioral wrinkle: a row the rep clearly intended (typed a name) but with an invalid or zero amount is silently dropped from the email with no indication in the preview. The rep could send a quote believing an add-on is included when it was filtered out. Not a correctness bug, but a usability gap worth a follow-up (e.g. flag invalid rows in the preview).

### HTML escaping of the service name

`a.name` is interpolated directly into a `<td>` with no escaping, so a service name containing `<`, `>` or `&` produces malformed HTML in the email. This is the same convention the file already uses for `clientName` and the plan `area`/`city`/`code` fields, so it is not a regression this change introduces, but the add-on name is the most free-form rep-typed string fed into the template so far (plan fields come from a controlled sheet). Flagged at **possible** confidence: impact depends on how tolerant the target email clients are and whether reps type special characters. A shared `escapeHtml` helper applied to `name` (and retrofitted to the other fields) would close it uniformly.

### No regression to existing dialog state

The new state, the four immutable handlers (`addAddonRow` / `updateAddonName` / `updateAddonAmount` / `removeAddonRow`), and the `setAddonServices([])` reset in the on-open effect sit alongside the existing `priceOverrides` / `removedRowKeys` logic without altering it. `addonServices` is in the `emailHtml` dependency array, so both Preview (`dangerouslySetInnerHTML={{ __html: emailHtml }}`) and Send (`html: emailHtml`) consume the same memoized HTML, and the reset-on-open prevents add-ons leaking between leads. The UI section is placed between Pricing Preview and Email summary as specified; the empty-list case shows only the "Add more service" button, satisfying the "click reveals the two columns" requirement. No new imports were added (`Button`, `Label`, `X` were already imported).

Not tested: build/typecheck cannot run in-sandbox (INTEGRATIONS_ONLY); correctness assessed by inspection. CI (`tsc --noEmit` + `bun run build`) will validate on the PR. No unit test covers the parse-and-filter predicate, which is the one piece of pure logic worth a test if the repo grows a suite.
