# Partial payment acknowledgment and auto-scheduled balance reminders

This change teaches the booking flow to distinguish partial payments from full ones. When a salesperson saves a booking with `payment_type: "partial"`, three things happen: the payment acknowledgment email renders a "PARTIAL PAYMENT" badge with the balance amount and due date instead of the generic "SUCCESSFUL" label; the `savedBookingData` state carries the new fields into the email builder; and two reminders (client + salesperson) are inserted into the `reminders` table scheduled for 9 AM on the due date.

Separately, the Booking ID lifecycle was hardened: the sheet-fetched ID is now prefetched on page load and re-fetched on dialog open, and the submit handler does a last-chance lookup if it still holds a local fallback.

**Watch for:** The reminder inserts pass the external booking ID string (e.g. "EMO-2025-001") to `reminders.booking_id`, which is a UUID FK referencing `bookings(id)` — this will fail at the database level on every partial-payment save (confirmed). The `send_at` timestamp has no timezone qualifier and will be interpreted as UTC by Supabase, so reminders fire at 9 AM UTC, not 9 AM IST (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The email template gained a conditional branch: when `payment_type` is `"partial"`, it renders an amber status badge, inserts balance-remaining and due-date rows into the summary table, and changes the status pill from green "SUCCESSFUL" to orange "PARTIAL PAYMENT". The plaintext fallback mirrors these additions.

The reminder auto-creation fires inside `onSuccess`, after the booking is persisted but as a fire-and-forget side-effect. It targets both the client and the salesperson at 9 AM on the due date. Two blocking issues exist here: the `booking_id` value passed is the wrong type (string instead of UUID), and the timestamp lacks timezone context, so the reminder won't fire at Indian business hours as intended.

The Booking ID refactoring is tangential to the partial-payment feature. It moves the sheet fetch earlier (prefetch on dashboard load, refetch on dialog open) and adds a submit-time re-fetch if the fallback is still present. This reduces the window where someone saves a locally-generated EMO-BK-* id, but introduces a subtle race: two users opening the form within the staleTime window could both receive the same sheet ID since there's no server-side reservation.

<details>
<summary>Issues (4)</summary>

1. **`booking_id` FK type mismatch** — The reminder inserts pass the external string ID (e.g. "EMO-2025-001") to `reminders.booking_id`, which is `uuid REFERENCES bookings(id)`. This will throw a Postgres type/FK error and the reminders will never be created. Fix: use `.insert(...).select("id")` on the bookings insert to get the generated UUID back, then pass that to the reminder inserts.
2. **`send_at` is UTC, not IST** — `${f.balance_due_date}T09:00:00` has no timezone offset. Supabase's `timestamptz` column will interpret it as UTC, so the reminder fires at 9 AM UTC (2:30 PM IST). Append `+05:30` or use a proper timezone-aware format.
3. **Reminder failures are silent** — Both reminder inserts are fire-and-forget `.then()` calls that log to console. The user gets no indication that their reminders weren't scheduled. At minimum, surface a toast warning on failure.
4. **Booking ID race between concurrent users** — The sheet ID is fetched client-side with a 60s staleTime. Two salespeople opening the form within that window get the same ID from cache; whichever saves second will hit a unique-constraint violation on `external_booking_id`. The submit-time re-fetch mitigates but doesn't eliminate this (both could re-fetch simultaneously).

## Reminder `booking_id` is the wrong type

The `reminders` table schema (`setup/ADD_REMINDERS.sql`) declares:

```sql
booking_id uuid REFERENCES public.bookings(id) ON DELETE SET NULL
```

The code passes:

```ts
booking_id: bookingId,  // e.g. "EMO-2025-001"
```

This is the external display ID, not the database UUID. Postgres will reject the insert with a type cast error or FK violation. Since the booking insert doesn't return the generated `id` (it uses `await supabase.from("bookings").insert({...})` without `.select("id")`), the UUID is never available to the reminder logic.

The fix requires chaining `.select("id").single()` onto the bookings insert to capture the auto-generated UUID, then threading it into both reminder inserts.

## Reminder timing fires at 9 AM UTC

The `send_at` value is constructed as:

```ts
send_at: `${f.balance_due_date}T09:00:00`
```

Since `f.balance_due_date` is a date string like `"2025-07-15"`, the final value is `"2025-07-15T09:00:00"` — no timezone offset. Supabase stores this in a `timestamptz` column and, absent explicit offset, interprets it as UTC. The reminder will fire at 2:30 PM IST rather than the intended 9 AM local time. For an Indian business audience, the string should be `"2025-07-15T09:00:00+05:30"`.

## Fire-and-forget reminder inserts with no user feedback

Both reminder inserts (client and salesperson) are detached promises:

```ts
supabase.from("reminders").insert({...}).then(({ error: remErr }) => {
  if (remErr) console.error("Failed to create client reminder:", remErr.message);
});
```

The `onSuccess` callback has already shown "Booking saved ✓" by this point. If the FK type mismatch (issue #1) causes both inserts to fail — which it will on every partial-payment save — the user will never know the reminders weren't scheduled. They'll expect the client and themselves to get notified, and neither will happen. A toast warning on failure would surface this without blocking the booking save.

## Booking ID race on concurrent saves

The wider staleTime (60s vs the previous 0) increases the window for two salespeople to pull the same "next unused" ID from cache. The unique constraint on `external_booking_id` catches the second save, but the error message (`duplicate key value violates unique constraint`) won't be particularly helpful to the user. The submit-time re-fetch reduces but doesn't eliminate the race since two simultaneous submissions could both re-fetch and receive the same id before either writes.
