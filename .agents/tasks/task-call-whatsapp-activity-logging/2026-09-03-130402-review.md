# Manual call & WhatsApp outcome logging on the lead page (review pass v1)

The Call and WhatsApp buttons on the lead detail page now fire the dialer/`wa.me` link and then open a shadcn dialog that captures a required outcome, optional duration (call only), and optional notes, persisted as a `lead_activities` row. This is the approved "Option A": purely manual, no telephony/WhatsApp API, no DB migration — the change reuses the existing `payload` JSONB column and the existing `activity_type` enum values `call`/`whatsapp`. `logActivity` gained an optional `payload` argument, and the timeline renders call/whatsapp rows with an icon, the outcome, and duration; every other activity type renders as before. The change is confined to `src/routes/_authenticated/leads/$id.tsx` plus a `RadioGroup` import.

Watch for: (1) initiating a call/WhatsApp no longer guarantees a timeline entry — if the rep dismisses the dialog, nothing is logged, a behavioral change from the old always-log button (confirmed); (2) the fire-then-open sequence navigates the tab via `window.location.href` before opening the dialog, which is safe-ish on mobile but can drop the dialog on desktop where `tel:`/`wa.me` may replace the page (confirmed); (3) duration input is unvalidated — negative and malformed values parse through or persist as invisible text (confirmed).

**Verdict**: APPROVED

## High-level view

The logging path is a clean extension: `logActivity` takes an optional `payload` and writes `payload ?? {}`, so the eight pre-existing callers are unchanged and keep writing an empty object. The insert is type-valid because `lead_activities.Insert.payload` is optional (`payload?: Json`) even though the Row type has it non-nullable, so no migration is needed and none was added.

The interaction dialog is a single shared component keyed by a `{ channel }` state object, adapting its title, outcome set, and duration field to call vs whatsapp. Outcome is a required RadioGroup, Save is gated on it, and fields reset on both close paths.

The behavioral shift worth weighing is that logging is now gated on the rep completing the dialog. Previously, clicking Call wrote a `call` activity unconditionally; now a cancelled or dismissed dialog leaves no record, and the phone number that used to land in the activity body is no longer captured. Whether that trade (richer intentional logs vs guaranteed-but-thin logs) is acceptable is a product call, but it's a real change in what the timeline captures.

Duration handling is lenient: `Number.parseFloat` accepts trailing garbage and negatives, and unparseable input is stored as `durationText` but never surfaced in the timeline (which only reads `durationMin`), so a rep who types a non-numeric duration sees it silently vanish from the timeline while it persists in the payload.

1. **Dismiss = no log** — cancelling or ESC-closing the dialog records nothing, unlike the old button which always logged a call/whatsapp. Confirm this is the intended trade; if not, consider a lightweight fallback log on dialer fire.
2. **Desktop fire-then-open** — `window.location.href = tel:/wa.me` runs before the dialog opens; on desktop this can navigate/replace the SPA and lose the dialog. Consider `window.open`/anchor with `target` or only firing navigation on mobile.
3. **Unvalidated duration** — negative and multi-dot values parse through (`-5`, `3.5.5` → `3.5`); no clamp or min. Add basic validation (non-negative, integer or single-decimal) if duration is meant to be trustworthy.
4. **Unparseable duration silently dropped from timeline** — `durationText` persists but the timeline only shows `durationMin`, so "5 mins" stored as text never appears. Either normalize display to fall back to `durationText`, or reject non-numeric input.
5. **Phone number no longer in body** — old logs stored `Phone: <mobile>` in the activity body; new logs store notes or nothing. Minor info regression; add mobile to payload if that history is useful.

### Fire-then-open sequencing and the dismissal gap

Both buttons run `window.location.href = ...` and then `setLogInteraction({ channel })` synchronously. The code comment documents the assumption that on mobile the browser tab survives behind the OS dialer/WhatsApp app, so the rep returns to a waiting dialog. That holds on mobile. On desktop the behavior is shakier: `tel:` and `wa.me` may be handled by navigating the current tab (protocol handler prompt, or a full navigation to web.whatsapp), which can tear down the SPA and the just-opened dialog with it. A `window.open(..., "_blank")` or an anchor click for the whatsapp case would keep the current tab (and dialog) intact; `tel:` is inherently OS-dependent.

The larger behavioral change is the logging gate. The previous code logged the call/whatsapp unconditionally on click:

```
onClick={() => { window.location.href = `tel:${lead.mobile}`; logActivity("call", `Called ${lead.client_name}`, `Phone: ${lead.mobile}`); }}
```

Now the row is only written when the rep picks an outcome and hits Save. A rep who fat-fingers Call, or gets voicemail and closes the dialog, leaves no trace. That's the point of Option A (only real outcomes get logged), but it means "number of call activities" is no longer a proxy for "dial attempts," and the phone number that used to be recorded in the body is gone. If dial-attempt history matters, a minimal fallback log on fire (later enriched by the dialog) would preserve it; otherwise document the intent.

### Duration parsing and timeline asymmetry

```
const parsed = Number.parseFloat(durationText);
const durationMin = channel === "call" && durationText && Number.isFinite(parsed) ? parsed : undefined;
...
...(durationText ? { durationText } : {}),
...(durationMin != null ? { durationMin } : {}),
```

`Number.parseFloat` is permissive: `"3 min"` → `3`, `"3.5.5"` → `3.5`, `"-5"` → `-5`. Negative and lossy values pass straight into `durationMin` with no clamp. Separately, when the input is non-numeric (`"five"`), `durationMin` is undefined but `durationText` is still persisted — and the timeline renders only `durationMin`:

```
{a.type === "call" && a.payload.durationMin != null && ` · ${a.payload.durationMin} min`}
```

So a stored-but-unparseable duration is invisible in the timeline while living in the payload. Either reject non-numeric duration at input, or have the timeline fall back to `durationText` so what the rep typed is always visible. For a manual field this is low-severity, but it's an inconsistency between what's stored and what's shown.

### Timeline guard protects historical rows

The timeline guard `(a.type === "call" || a.type === "whatsapp") && a.payload && a.payload.outcome` means historical call/whatsapp rows without a structured payload — and the separate `followup` insert at line 1041 that doesn't pass payload — fall through to the plain title/body rendering, so nothing regresses for existing data.

### Not tested

No automated tests exist in the repo and none were added; verification is by inspection and PR CI (`tsc --noEmit` + build). Not exercised: dismissal-without-save producing no row, duration parsing edge cases (negative, non-numeric, multi-dot), the desktop fire-then-open path, and per-channel outcome sets rendering. Manual QA on a real mobile device is worth doing before shipping.
