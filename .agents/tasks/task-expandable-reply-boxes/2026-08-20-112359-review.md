# Expandable reply/compose boxes across inbox and reminders

This change converts three compose areas — the inbox reply composer, the quotation composer, and the reminders schedule dialog — from fixed-size inline forms into expandable full-screen dialogs. Each composer gains a Maximize2/Minimize2 toggle whose state persists in localStorage, and the inbox reply composer picks up a template/snippet dropdown (matching the quotation composer's existing UX). The expanded dialogs use a consistent flex-col layout pattern with growing text areas.

Watch for: the reply template applies quotation-oriented templates (including pricing placeholders) to a plain-text reply composer, which produces confusing output for the end user (confirmed). The `replySubject` field shown read-only in the expanded reply dialog is never explicitly set in the new code paths — it relies on a pre-existing derivation that may be empty for certain threads (likely). localStorage expand preferences survive thread changes, so opening any email auto-expands the reply box if the user previously expanded it on a different thread (confirmed, intentional per localStorage pattern but worth noting as UX friction).

**Verdict**: APPROVED

## High-level view

The expandable pattern is a boolean state + localStorage key + Dialog overlay. The inline composer hides itself (`!replyExpanded` guard) when expanded, and the Dialog takes over full-screen. The same pattern is applied in three places with minor layout differences (reply uses a plain Textarea, quotation uses a Textarea with calculator, reminders uses a RichTextEditor).

The template dropdown added to the reply composer reuses `QUOTATION_TEMPLATES` — templates designed for formal quotations with pricing placeholders — and injects them as plain text into a Textarea via naive HTML stripping. The reply composer's "Quotation" template produces "Service: [enter service]Price: [enter amount]" as a run-on line because `<li>` tags are stripped without newline insertion.

The reminders dialog gains its own `REMINDER_TEMPLATES` array with purpose-built templates (Welcome, Follow-up, Documents, Payment, Thank you, Blank) that produce full HTML bodies fed directly into the RichTextEditor.

## Template reuse and HTML-to-plaintext gap

The inbox reply composer calls `applyReplyTemplate` which first checks whether the selected ID matches a DB snippet, and falls back to `buildQuotationTemplate` — the same function powering the quotation composer. These templates include HTML with `<ul>` lists and styled `<span>` elements. The reply composer is a plain `<Textarea>`, so the function strips HTML via chained `.replace()` calls:

```tsx
snippet.body_html
  .replace(/<br\s*\/?>/gi, "\n")
  .replace(/<[^>]+>/g, "")
  .replace(/&amp;/g, "&")
  .replace(/&lt;/g, "<")
  .replace(/&gt;/g, ">")
  .replace(/&nbsp;/g, " ")
```

This handles `<br>` → newline, but `<li>` tags are silently dropped without inserting newlines or bullet markers. The quotation template's structured list collapses into a single run-on line. For "Blank" and "Thank you" templates (mostly prose with `<br>` breaks), the output is fine. For "Quotation" and "Documents" (which use `<ul>/<li>`), it's garbled. A follow-up could add `\n` before `</li>` stripping or provide plain-text variants of the templates.

## Expand state lifecycle across threads

The `reading?.threadId` effect resets `replyOpen` and `replyText` but not `replyExpanded`. Similarly, `openQuotationComposer` no longer calls `setQuotationExpanded(false)` and the success/cancel handlers no longer reset it. This means switching threads preserves the user's expand preference — intentional per the localStorage persistence feature, but it creates a situation where a user who expanded once for a detailed reply will get full-screen mode on every subsequent quick reply until they manually collapse it.
