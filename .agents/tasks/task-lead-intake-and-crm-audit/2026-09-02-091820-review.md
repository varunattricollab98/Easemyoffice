Second review pass after commit `c7ab9ec` addressed the two confirmed defects from v1 and documented the deferred trade-offs. The PostgREST `.or()` email-injection surface is gone: the dedup step now runs two parameterized `.eq()` lookups (mobile, then email) merged in code, and a strict `EMAIL_RE` rejects whitespace and filter metacharacters before the email is ever used or stored. The `balance-reminders` 503 path no longer echoes the raw error — it logs server-side and returns a generic `internal error`. The remaining v1 items (fail-open token + no rate limit, dedup race with no unique index, claim-RLS-applied-on-prod) were intentionally not code-fixed and are now documented prominently. ## High-level view

The injection fix is genuine, not cosmetic. The old `.or(\`mobile.eq.${mobile},email.eq.${email}\`)` string is fully removed; no remaining code path interpolates a caller value into PostgREST filter syntax. Mobile was already reduced to `+` and digits, and email now passes through `normalizeEmail`, which excludes comma, parens, quotes, backtick, backslash and whitespace — the exact metacharacters that made the `.or()` exploitable. The two-`.eq()`-with-merge approach preserves the external contract: dedup by mobile OR email, append message, return `{ deduped: true }`.

The balance-reminders leak is closed: the real error goes to `console.error`, the response body is a fixed `internal error` string, status unchanged at 503.

The three deferred items are handled as documentation, and the deferral is reasonable for this pass. `CONTACT_FORM_INTAKE.md` leads its anti-abuse section with a boxed warning that the endpoint is an open, RLS-bypassing write path until `LEAD_INTAKE_TOKEN` is set, calls the token a required production step, and lists rate-limiting/captcha as an explicit follow-up. The dedup race is documented there and in a code comment at the dedup block as an accepted best-effort trade-off pending a unique index. The claim-RLS-applied-on-prod question — unverifiable from this sandbox — is tracked in `USER_ACTIONS.md` with paste-and-run steps and an end-to-end verification procedure.

The one new observation is the insert-failure error leak on the intake endpoint, which mirrors the balance-reminders bug just fixed — lower severity (only fires on an actual DB insert error, not every probe) and non-blocking, but an asymmetric loose end.

The "0-to-hero" second ask (auto-assignment, auto-scoring of web-form leads, deploying the two missing edge functions, global search) remains handed back as a backlog rather than implemented. Scoping the change to the intake endpoint plus hardening and carrying the broader feature work as separate follow-ups is the right call for a hardening pass.

### PostgREST `.or()` injection — closed

The v1 blocking defect interpolated the caller email into `.or(\`mobile.eq.${mobile},email.eq.${email}\`)`, where commas/dots/parens are structural to PostgREST. That branch is gone. The dedup now reads:

```ts
const { data: byMobile } = await supabaseAdmin
  .from("leads").select(selectCols).eq("mobile", mobile).limit(1).maybeSingle();
let existing = byMobile;
if (!existing?.id && email) {
  const { data: byEmail } = await supabaseAdmin
    .from("leads").select(selectCols).eq("email", email).limit(1).maybeSingle();
  existing = byEmail;
}
```

`.eq()` passes the value as a bound argument, not as filter-string syntax, so a value containing `,` or `.` cannot alter the query shape. `normalizeEmail` rejects those characters up front regardless:

```ts
const EMAIL_RE = /^[^\s,()"'`\\@]+@[^\s,()"'`\\@]+\.[^\s,()"'`\\@]+$/;
```

An invalid or metacharacter-laden email normalizes to `null`, so it is neither stored nor used in the lookup. Mobile remains safe via `normalizePhone` (leading `+` and digits only). The dedup contract is intact: mobile is checked first, email only if mobile misses, a match appends the timestamped message to `notes` and returns `{ ok: true, deduped: true, lead_id }`.

### Carryover: intake insert-failure still leaks the DB error

The same leak class the fix closed on balance-reminders is still open on the intake endpoint's insert path:

```ts
if (error || !created) {
  return json({ ok: false, error: error?.message ?? "insert_failed" }, 500);
}
```

On a DB insert failure this returns the raw Postgres/PostgREST error string to an unauthenticated caller. Narrower than the balance-reminders case (it only fires on an actual insert error, not a schema/init probe), so it doesn't block, but it should log server-side and return a generic message like the balance-reminders handler now does.

### Deferred trade-offs — documentation verified

Fail-open token and missing rate limit (v1 issue 2) and the dedup race (v1 issue 3) were intentionally not code-fixed. `CONTACT_FORM_INTAKE.md` opens its anti-abuse section with a boxed warning that the endpoint is a world-writable, RLS-bypassing service-role write path until `LEAD_INTAKE_TOKEN` is set, frames the token as a required production step, and lists rate-limiting/captcha as a planned follow-up. The dedup race is documented in the same file and restated in a code comment at the dedup block as an accepted best-effort trade-off pending a DB unique index. The fail-open default is a deliberate "works out of the box" choice and the race window is narrow, so deferring both with prominent documentation is acceptable for this pass.

The claim-RLS-applied-on-prod question (v1 issue 5) is inherently unverifiable from this sandbox and is tracked in `USER_ACTIONS.md` with the migration paste-and-run steps and an end-to-end claim-flow verification procedure.
