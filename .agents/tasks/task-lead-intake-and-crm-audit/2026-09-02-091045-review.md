# Public web-form lead intake + public-hook hardening for EaseMyOffice CRM (v1)

Adds an unauthenticated `POST /api/public/hooks/lead-intake` route that turns a website "Contact us" submission into an UNASSIGNED lead (`assigned_to NULL`, `stage new_lead`, `source website`) via the service-role client, so reps can claim it in the existing inbox/pipeline flow. It also hardens the pre-existing `balance-reminders` public hook with an optional shared-secret gate and a top-level try/catch (turning anonymous-probe 500s into structured JSON), promotes the claim-lead RLS fix from a loose `setup/*.sql` file into a tracked idempotent migration, and registers `LEAD_INTAKE_TOKEN` / `BALANCE_REMINDERS_TOKEN` in the `SERVER_ENV_KEYS` bridge. Typecheck is clean (0 errors) and the route is wired into `routeTree.gen.ts`.

**Watch for:** the dedup lookup interpolates the caller-supplied email straight into a PostgREST `.or()` filter string with no escaping — a **confirmed** filter-injection surface on an unauthenticated service-role endpoint. Also note the token guard on both hooks is fail-open by design (no secret configured ⇒ no auth), and the endpoint is world-writable to the `leads` table with no rate limiting.

**Verdict**: NEEDS_CHANGES

## High-level view

The intake route is the intended shape: multi-format body parsing so a raw HTML form or a `fetch()` both work, phone normalized to `+` and digits, `service`/`source` coerced against the `crm.ts` enums (unknown values dropped, not passed through), and an unassigned insert. Leaving `assigned_to NULL` and relying on the claim flow is consistent with the RLS migration shipped alongside it.

The one blocking defect is in the dedup step: `email` is interpolated verbatim into `.or(...)` after only an `@` presence check, while `mobile` is safe because `normalizePhone` reduces it to `+` and digits. PostgREST treats commas and dots inside the `.or()` argument as structural, so a crafted email lets an anonymous caller alter a filter that runs under the service role. It does not reach an insert, but an unauthenticated attacker steering a server-side query should be closed before shipping.

The anti-abuse posture is intentionally light: a honeypot plus a token enforced only when its env var is set. Both hooks are fail-open until the user configures secrets in Cloudflare, and the intake is otherwise an open write path into `leads` with no rate limit — abuse resistance depends entirely on the operator setting the token.

The balance-reminders hardening returns a 503 JSON body instead of an unhandled 500 on any throw, and reads the token from a header or a cloned body so the stream stays readable — but it echoes the raw error message back to unauthenticated callers. The claim RLS migration is idempotent and its `WITH CHECK` still forces the claimer to become the owner, so it can't hand a lead to another rep; whether it is applied to prod is unverifiable here and flagged for the user.

<summary>Details</summary>

### Email interpolated into the service-role `.or()` filter

The dedup branch builds its filter as a string:

```ts
if (email) {
  dedupQuery = dedupQuery.or(`mobile.eq.${mobile},email.eq.${email}`);
} else {
  dedupQuery = dedupQuery.eq("mobile", mobile);
}
```

`email` is `emailRaw.toLowerCase()` gated only by `emailRaw.includes("@")`. PostgREST parses the `.or()` argument as a comma-separated list of `column.op.value` clauses, so commas, dots, and parentheses in the value are structural, not literal. An anonymous caller can submit `email=a@b.co,assigned_to.not.is.null` (or richer payloads) and change which rows the service-role query matches. The `mobile` side is not exposed because `normalizePhone` strips everything except a leading `+` and digits — the same discipline just isn't applied to email.

This is on an unauthenticated endpoint using the service-role client that bypasses RLS, so it is the higher-severity item in the change. It does not by itself write attacker-controlled data (the subsequent insert uses fixed columns), and the worst directly-reachable outcome is a manipulated dedup match that appends a message to, or skips creation against, an unintended existing row — but a caller steering a server-side query under the service role is exactly the trust-boundary issue this endpoint class exists to guard. Fix by not string-building the filter: validate the email against a real pattern and reject metacharacters, or run two `.eq()` lookups (`mobile`, then `email`) and merge in code, which sidesteps PostgREST filter syntax entirely.

### Fail-open token guard and open write surface

Both hooks enforce the shared secret only when the env var is present:

```ts
const expectedToken = process.env.LEAD_INTAKE_TOKEN;
if (expectedToken) { /* compare, else 401 */ }
```

This matches the documented "works before the user configures a secret" behavior, so it is a deliberate trade-off. The consequence worth stating plainly: until the operator sets `LEAD_INTAKE_TOKEN` in Cloudflare, anyone who finds the URL can create `leads` rows through the service-role client, with no rate limiting or captcha behind the honeypot. The honeypot stops naive bots but not a targeted script. The token should be strongly recommended (not merely optional) in the setup doc, and rate limiting considered.

### balance-reminders error-message leak

The prior handler could throw before returning (service-role init, DB call, network) and surface as an unhandled 500 error page to anonymous probes; the wrap now returns a `503` JSON `{ ok:false, error }` on any throw, with the token check inside the same try. One gap remains: the raw error `message` is echoed back in the 503 body — fine for an internal cron target, but it leaks internal error strings to an unauthenticated caller when no token is set. Trim to a generic message.

### Claim-lead RLS migration

The migration promotes `setup/FIX_LEADS_CLAIM_RLS.sql` verbatim into `supabase/migrations/20260515000001_fix_leads_claim_rls.sql`. It is safe to re-run (`DROP POLICY IF EXISTS` then `CREATE POLICY`); the `USING` clause adds `OR assigned_to IS NULL` so a rep can claim an unassigned lead, while `WITH CHECK` omits that branch — after the update the row must be owned by the claimer (or admin/cross-team role), so the policy can't be used to reassign a lead to a third party. That asymmetry between `USING` and `WITH CHECK` is the correct construction for a claim operation. Whether it is live on prod is unverifiable here and remains a user action.

### 0-to-hero CRM gaps (from the user's second ask)

The user asked what a complete sales CRM should still have; the audit enumerates this and none of it is implemented in this diff — correctly, since a review pass shouldn't bundle broad feature work. The material gaps to carry into follow-up features, in priority order: **auto-assignment / lead routing** (inbound leads are all unassigned and claimed manually — no round-robin or rule-based owner assignment), **auto-scoring of inbound web-form leads** (`calcScore`/`deriveInterest` exist but only run off manual intent flags in the New Lead dialog, so website leads land with the default score of 0), **SLA / stale-lead escalation** and **scheduled report emails** (both edge functions exist in-repo but return 404 = not deployed to prod), and a **global search omnibox** across leads/bookings/clients (only per-page search exists today). Each should become its own feature rather than expanding this change.

### Not tested

There is no unit/integration coverage for the intake route (the project has no unit runner, only Playwright e2e, and none was added). Untested behaviors that matter: the injection payload above, the dedup race under concurrent posts, phone normalization edge cases (short/international numbers), and the 401 path when the token is set. Verification here is limited to typecheck (0 errors) and build; runtime correctness against the live Supabase schema is unverified from this sandbox.
