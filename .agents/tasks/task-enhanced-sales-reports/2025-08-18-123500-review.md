# Enhanced sales reporting suite (daily/weekly/monthly)

Three Supabase Edge Functions now generate periodic sales performance reports delivered via Resend email. The daily report was rewritten to add revenue tracking, closing rate, day-over-day improvement percentages, ranking, and a base64 CSV attachment. Two new functions—weekly and monthly—extend the same pattern with week-over-week and month-over-month comparisons, top/bottom performer highlighting, team-average comparisons in individual emails, and (monthly only) target-vs-actual from a `user_targets` table. All three share a cron-secret auth gate, build rich HTML emails, and attach CSV data for admins.

Watch for: booking-to-agent matching is a brittle name-string lookup that silently drops bookings on any whitespace or spelling mismatch (confirmed); the `btoa()` call on CSV content will throw on any non-ASCII character in salesperson names, crashing the entire function (confirmed); individual emails are sent sequentially with no `fetch()` exception guard—one network error mid-loop aborts delivery for all remaining recipients (confirmed); auth check short-circuits on empty `CRON_SECRET` returning 401 even for legitimate callers, making the function un-invocable until the secret is deployed (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The three functions share an identical architectural skeleton: authenticate via cron secret → fetch profiles and role lists → aggregate activities/bookings/leads/followups for two adjacent time windows → compute derived metrics (improvement %, closing rate, ranking) → build HTML + CSV → send emails via Resend. Code duplication across functions is substantial (~80 lines of aggregation logic verbatim), but acceptable given Supabase Edge Functions' inability to share code across function directories.

Booking attribution relies on a name-based join (`sales_agent_name` lowercased → profile `full_name` lowercased). Any mismatch—extra whitespace, abbreviation, partial name—causes the booking to vanish from the stats silently. This is the single most likely silent-failure mode in production.

The monthly report adds a time-to-close heuristic that greedily matches the closest lead creation date before each booking date across *all* historical closed leads—not scoped to the reporting month. This produces misleading averages when agents have long lead histories.

CSV generation uses `btoa()` which only handles Latin-1 characters. Indian names in Devanagari or other non-Latin scripts will crash the function with an `InvalidCharacterError`, preventing the entire report from sending.

Individual salesperson emails are dispatched in a serial `for...of` loop. The loop handles HTTP-level errors gracefully, but an unhandled `fetch()` exception (timeout, DNS failure) propagates to the top-level catch and aborts the remaining sends with no record of which emails already succeeded.

<details>
<summary>Issues (7)</summary>

1. **Name-based booking attribution** — `sales_agent_name` is matched case-insensitively but with no whitespace trimming or fuzzy tolerance. A trailing space or abbreviation silently drops bookings from stats. Add `.trim()` at minimum; prefer a `user_id` FK on bookings long-term.
2. **`btoa()` crashes on non-ASCII names** — Replace `btoa(csvContent)` with a UTF-8-safe encoder (`btoa(unescape(encodeURIComponent(csvContent)))` or Deno's `std/encoding/base64`).
3. **Sequential email dispatch without exception guard** — Wrap each `fetch()` call in its own try/catch so a network exception doesn't abort remaining sends. Consider `Promise.allSettled()` for parallelism.
4. **Empty CRON_SECRET denies all requests** — The `!CRON_SECRET` guard makes the function permanently return 401 when the env var isn't set. Add a distinct error message ("CRON_SECRET not configured") so operators can distinguish configuration issues from bad credentials.
5. **Time-to-close heuristic is misleading** — Monthly report matches booking dates against all-time closed leads, not scoped to recent months. This pairs bookings with unrelated historical leads. Scope the query to leads created within the last 90–180 days.
6. **Daily report omits salespeople with zero activity today** — `allUserIds` is built from `currentStats.keys()` only. A person active yesterday but idle today shows no "-100%" row. Build the set from both `currentStats` and `previousStats` keys.
7. **CSV quoting incomplete** — The `improvement` field contains "+" and "%" characters; `closingRate` contains "%". While not strictly breaking, the `name` field only quotes on commas. Consider quoting all string fields for RFC 4180 compliance.

## Booking attribution via name string

All three functions join bookings to users through a name-string lookup:

```ts
const nameToId = new Map<string, string>();
for (const p of profiles ?? []) {
  if (p.full_name) nameToId.set(p.full_name.toLowerCase(), p.id);
}
// later:
const uid = nameToId.get(b.sales_agent_name.toLowerCase());
```

No `.trim()` is applied, so a trailing space in either field causes a miss. If the bookings table stores a display name while the profile stores a formal name ("Raj" vs "Rajesh Kumar"), the join silently drops the booking. The consequence is under-reported revenue and bookings for individual salespeople with no error trail—admins would see correct totals from the bookings table but deflated per-person numbers in the report.

## `btoa()` and non-Latin characters

```ts
const base64CSV = btoa(csvContent);
```

`btoa()` in Deno throws `InvalidCharacterError` if the input contains any character outside the Latin-1 range (code points > 255). A single salesperson name in Hindi/Tamil/etc. crashes the entire function, preventing the report from being sent to anyone. Fix:

```ts
const base64CSV = btoa(unescape(encodeURIComponent(csvContent)));
```

## Sequential email loop without exception isolation

Weekly and monthly functions send individual emails in a `for...of` loop:

```ts
for (const user of salesBdUsers) {
  const indRes = await fetch("https://api.resend.com/emails", { ... });
  if (!indRes.ok) {
    emailResults.push({ type: "individual", to: user.email, ok: false, error: ... });
  } else {
    emailResults.push({ type: "individual", to: user.email, ok: true });
  }
}
```

HTTP-level errors (4xx/5xx) are recorded and the loop continues. But if `fetch()` itself throws (timeout, connection reset), the exception propagates to the top-level `catch (e)` and the function returns `{ ok: false, error: ... }` with no record of which emails already succeeded. For a team of 20+ people, sequential dispatch also creates latency risk against the Edge Function timeout (default 150s).

## Monthly time-to-close heuristic

```ts
const { data: closedLeads } = await supabase
  .from("leads")
  .select("assigned_to, created_at, stage")
  .in("stage", ["Booking Done", "booking_done", "Booked", "booked", "Won", "won", "Closed Won", "closed_won"]);
```

This fetches *all* closed leads for *all time*. The matching logic then picks the lead with the smallest positive `(bookingDate - leadCreationDate)` for each booking. An agent with many historical leads will have spurious matches—a lead created 11 months ago that happens to be the "closest" before this month's booking produces an inflated 330-day time-to-close. The query should be scoped to leads created within the reporting month (or at most the preceding 90 days).

## Daily report scope asymmetry

```ts
const allUserIds = new Set<string>([...currentStats.keys()]);
```

A salesperson who was active yesterday but had zero activity today won't appear in `rows`. Their improvement is logically "-100%", but they're invisible in the main table. The `inactiveUsers` section catches people with zero calls/emails/whatsapp, but not people who had some activity yesterday and none today in all categories. Weekly and monthly functions have the same pattern—`allUserIds` is populated only from current-period stats.
