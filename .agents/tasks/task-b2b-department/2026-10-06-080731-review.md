# B2B department module for EaseMyOffice CRM (v1)

A complete, additive B2B department bolted onto the existing CRM across 10 commits: a new `b2b` app_role, ten new Postgres tables (nine core + `b2b_onboarding`) with hand-written RLS, a CA-firm-as-account data model with contacts/leads/activities/follow-ups/partnerships/referrals, a 7-step CSV import, firm 360, partnership pipeline, referral→Sales-lead/booking linkage, partner scoring and performance, a B2B dashboard + analytics suite, partner-health renewals, an onboarding checklist, employee-facing `/my-payroll`, and an admin cross-module command center with KPI drill-down. The work is cleanly isolated: it only CREATEs new `public.*` tables, extends a handful of union types and nav arrays, and reuses the established `hrmsDb()`-style `b2bDb()` escape-hatch for tables absent from the generated Supabase types. Build, typecheck and the 243-test suite (112 new) are green.

Watch for: (1) the admin command center reads `salary_slips.net_pay` to compute a payroll-cost KPI — correct for admins and RLS-protected, but it is the one place salary figures are touched, so the admin-only gating is load-bearing (confirmed safe). (2) The CSV import commits firms→contacts→leads as separate non-atomic chunked REST calls, so a mid-import failure leaves a partial import whose batch counts overstate what landed (confirmed, inherent to the REST client). (3) `b2b_activities`/`partnerships` write policies narrow to `created_by`-only on update/delete while their SELECT inherits firm ownership — an asymmetry, likely intentional but worth confirming against the product intent.

**Verdict**: APPROVED

## High-level view

The permission story is the heart of this change and it holds up. All ten new tables ENABLE RLS with an admin-full + owner-scoped shape mirroring the existing HRMS/leads pattern; child tables (contacts, activities, follow-ups, onboarding) reach access through an EXISTS sub-select on the parent firm's ownership. There is no path for a non-admin B2B user to read rows they neither own, are assigned, nor created. Salary isolation is intact: `/my-payroll` queries only attendance/leave for the caller's own employee row and never touches `salary_slips`/`employee_salary`; those tables stay admin-only, and the only new code that reads them is the admin-gated command center.

The change is strictly additive. Zero existing migrations were modified, zero edge functions touched (`attendance-punch`, `hr-requests` byte-unchanged), and the handful of edits to shared files — `AppRole`, `AuditEntity`, `ROLE_OPTIONS`, the bookings `?source=` param, the dashboard command view — are all union/optional extensions that preserve existing behaviour.

Functionality is real, not mocked. Pages read and write through `b2bDb()` and the query modules; the import pipeline classifies, dedupes, assigns and bulk-inserts actual rows with batch tracking; the referral→lead conversion inserts a valid `public.leads` row using `source="referral"` and a `service_type`-enum-constrained service, satisfying the live schema and never mutating existing Sales records.

The pure maths (scoring, funnel, analytics, follow-up bucketing, command-center summaries) live in DB-free `src/lib/*.ts` modules with concrete-value unit tests that would fail on reversion. The one durability caveat is the non-transactional multi-table import; the one design question is the write-policy asymmetry on activities/partnerships.

### RLS boundary across the ten new tables

The real access boundary is the SQL, since the frontend hiding is cosmetic and the REST API is directly reachable. Every table in `20260517000002_b2b_core.sql` and `b2b_onboarding` in `20260517000003_b2b_documentation.sql` runs `ENABLE ROW LEVEL SECURITY` and defines explicit SELECT/INSERT/UPDATE/DELETE policies. The pattern is consistent:

```
admin (is_admin(auth.uid()))              -> full CRUD
b2b   (has_role(auth.uid(),'b2b')) + own  -> read/update own rows; insert pins created_by = self
```

Parent-owned child tables (`b2b_contacts`, `b2b_activities`, `b2b_followups`, `partnerships`, `b2b_onboarding`) resolve "own" through an `EXISTS` sub-select against `ca_firms` ownership (`owner`/`assigned_to`/`created_by`) and/or the parent lead. A non-admin B2B user's SELECT on `ca_firms` is constrained to `owner = auth.uid() OR assigned_to = auth.uid() OR created_by = auth.uid()`, and `b2b_leads` to `assigned_to`/`created_by` — there is no readable path to firms or leads assigned to a different user. INSERT policies force `created_by = auth.uid()` (and `uploaded_by = auth.uid()` for batches), so a user cannot forge ownership. DELETE on the primary tables is admin-only.

One asymmetry to confirm rather than fix: `b2b_activities` UPDATE/DELETE and `partnerships` UPDATE narrow to `created_by` (plus `assigned_to` for partnerships), while their SELECT inherits firm ownership. So a firm owner who did not create an activity logged against their firm can read it but cannot edit or delete it. That is a defensible "author owns their note" model, but it diverges from the firm-ownership read model and is worth an explicit product decision.

### Salary isolation

The hard requirement — an employee never sees another employee's salary, and never sees their own salary amounts in V1 — holds. `src/routes/_authenticated/my-payroll.tsx` reads `employees` (scoped `profile_id = auth.uid()`), `attendance`/`leave_requests` for that own employee id, and reference tables (`hr_settings`, `holidays`); it computes LOP/paid-days through the shared `payroll.ts` helpers and renders no amount. It issues no query against `salary_slips` or `employee_salary`.

The only new code reading salary is `command-center-queries.ts:331` (`salary_slips` `status, net_pay`), aggregated into a month payroll-cost KPI. This surfaces only inside the command center, which is lazy-loaded exclusively from the admin-gated dashboard branch (`dashView === "command" && isAdmin`) with no standalone route, and `salary_slips` RLS is admin-only regardless. The gating is therefore defence-in-depth over an already-closed DB boundary.

### Additivity and backward-compat

Only three new migration files exist; `git diff` confirms no existing migration changed and `supabase/functions/` has zero diff. The shared-file edits are all extensions:

- `auth.tsx`: `AppRole` gains `"b2b"`.
- `audit.ts`: `AuditEntity` union gains `ca_firm | b2b_lead | referral`.
- `admin/users.tsx`: `ROLE_OPTIONS` gains `"b2b"`; the `role as never` casts are the expected consequence of the generated `user_roles` type not yet knowing the new enum value (same rationale as `b2bDb()`).
- `bookings.tsx`: adds an optional `?source=` search param that substring-filters `booking_source`; absent the param, filtering and direct navigation are unchanged.
- `dashboard.tsx`: adds an admin-only `"command"` view, double-gated on `isAdmin` so a non-admin cannot reach it by forcing state.

Nav entries in `app-shell.tsx` are all `roles: ["admin","b2b"]`, keeping B2B out of other roles' sidebars; `/my-payroll` is intentionally role-agnostic so every department (including B2B) sees their own readiness.

### Referral → Sales lead/booking linkage

`convertReferralToLead` (`b2b-queries.ts:517`) inserts a brand-new `public.leads` row and writes its id back onto the referral — it never touches existing leads. The insert supplies `client_name`, `mobile`, `source`, `service_required`, `notes`, `created_by`. Against the live `leads` schema (`20260512095324`), the two enum-typed NOT NULL columns are the risk:

- `source public.lead_source` — the call site passes the literal `"referral"`, a valid enum member.
- `service_required public.service_type` — seeded from `SERVICES` in `crm.ts`, whose ids (`virtual_office`, `gst_registration`, `apob`, `business_registration`, `iec`, `trademark`, `other`) are exactly the enum members, and the dialog `Select` only offers those, defaulting to `virtual_office`.

So the insert satisfies the schema and enum constraints; `lead_code` auto-defaults from its sequence. `linkReferralBooking` only updates referral columns and reads bookings read-only via `listLinkableBookings`, so Sales/booking rows are never mutated. The cross-module FKs (`referrals.lead_id`/`booking_id`) are `ON DELETE SET NULL`, so deleting a Sales record preserves B2B history.

### 7-step CSV import

`b2b-import.ts` holds the pure core: four dedupe keys (last-10-digit phone, lower-cased email, firm+city composite, host-normalised website), validation (firm name + at least one usable contact, with malformed-phone/email reasons), classification that catches both existing-record and within-file duplicates (first occurrence wins), and deterministic round-robin/specific/team assignment. `import.tsx` wires these to the DB: it records a batch with full counts, dedupes firms by firm+city within the upload, then bulk-inserts firms → primary contacts → leads in 200-row chunks, each stamped with `import_batch_id` and the resolved `assigned_to`, and logs an audit entry. Import history reads back through the batch table.

The durability gap: these are separate, non-transactional REST inserts. If `bulkInsertLeads` (or the contacts pass) throws after firms are committed, the firms/contacts persist, the leads are missing, and the batch row's `new_records`/`assigned_records` overstate what actually landed — with no rollback. Supabase's REST client has no client-side multi-statement transaction, so this is an inherent constraint rather than a coding slip, but the import summary currently reports the planned counts, not the realised ones; a partial failure would be invisible to the user. A server-side RPC/edge function or a post-insert reconcile would close it.

### Pure maths and test quality

Scoring (`b2b-scoring.ts`), follow-up bucketing (`b2b-followups.ts`), performance aggregation (`b2b-performance.ts`), analytics (`b2b-analytics.ts`) and command-center summaries (`command-center.ts`) are all DB/React-free and take `now` as a parameter, so they are deterministic. `partnerScore` is clamped and monotonic with caps summing to 100; `partnerHealthCategory` gates on recency/history, not score alone; `bucketFor` compares IST calendar-day keys so a follow-up due earlier today reads as Today, not Overdue. The tests assert concrete input→output values (conversion counts, revenue sums, bucket membership at day boundaries, round-robin distribution) and would fail on reversion — not smoke tests. 243 pass across 18 files.
