# Documentation workflow: tasks table, post-booking assignment, and dashboard

This change introduces a `documentation_tasks` table (with a 9-stage enum) to model the lifecycle of documents tied to a booking. After saving a booking in the new-booking dialog, a new "Assign to Documentation" step lets the user pick a documentation-role team member. The documentation page is rewritten from a leads-based virtual list to a purpose-built task dashboard with stats cards, time-period filtering, search, and per-row stage-change dropdowns. RLS policies gate visibility and restrict mutations (sales/bd/admin can insert, admin/assigned can update).

Watch for: the SELECT policy grants *all* documentation-role users visibility of *every* task, which contradicts the stated requirement that "documentation person sees only their assigned tasks" (**confirmed**); the stage-change dropdown permits arbitrary jumps (including backward) with no guard (**confirmed**); and the `docAssignBookingId` can be null if the Supabase insert doesn't return an id, silently skipping assignment without user feedback (**likely**).

**Verdict**: NEEDS_CHANGES

## High-level view

The SELECT RLS policy is overly broad — it exposes all tasks to anyone with the `documentation` role, not just their own. The `OR public.has_role(auth.uid(), 'documentation')` clause defeats the stated requirement that documentation users only see tasks assigned to them. This also breaks the dashboard's assumption that non-admin users only see their own rows (it hides the "Assigned To" column accordingly).

The booking dialog's assignment flow depends on `bookingUuid` being non-null after the Supabase insert, but the dialog opens unconditionally after the acknowledgment step. If the UUID is null, `handleDocAssign` short-circuits without feedback — the user clicks "Assign" and nothing happens.

Stage transitions are unconstrained: any stage can jump to any other stage, including backward, with no confirmation or audit trail.

No unique constraint on `booking_id` means duplicate task rows can accumulate for the same booking through double-submits or re-triggered flows.

## RLS policy mismatch with requirements

The SELECT policy reads:

```sql
USING (
  public.is_admin(auth.uid())
  OR assigned_to = auth.uid()
  OR public.has_role(auth.uid(), 'documentation')
);
```

The third clause means any user with the `documentation` role can read every row in the table. The user requirement explicitly states "documentation person sees only their assigned tasks". The `assigned_to = auth.uid()` clause already covers their own tasks, making the `has_role` clause purely additive — it grants cross-user visibility. Removing that line brings the policy in line with the spec while preserving admin's full view and individual ownership.

The dashboard hides the "Assigned To" column for non-admin users (assumes they only see their own rows), but with the current RLS they'll see other people's tasks with no assignee context.

## Assignment flow null safety

The booking dialog chains three sequential UI gates: form → acknowledgment email → documentation assignment. The booking UUID flows through state:

```
submit.onSuccess → setDocAssignBookingId(bookingUuid)  // only if bookingUuid truthy
                 → then either setShowAckDialog or setShowDocAssignDialog
```

If the insert succeeds but `.select("id").single()` doesn't return data (possible with aggressive RLS or a Supabase edge case), `bookingUuid` is null, `docAssignBookingId` never gets set, and the documentation dialog opens anyway (triggered unconditionally after the ack step). Inside `handleDocAssign`, the `if (!docAssignBookingId || !selectedDocUser) return` guard prevents the insert but provides no feedback — the user clicks "Assign", nothing happens, no toast, no error.

Fix: if `bookingUuid` is null after the insert succeeds, either skip the documentation dialog with a warning toast, or surface the error and block.

## Stage transition model

The stage dropdown renders all 9 stages regardless of the task's current position:

```tsx
<SelectContent>
  {DOC_STAGES.map((s) => (
    <SelectItem key={s.id} value={s.id}>{s.label}</SelectItem>
  ))}
</SelectContent>
```

A task at `countersigned` can be moved back to `assigned` with a single click — no confirmation, no audit note. Filtering the options to `current stage + forward stages` (or offering all with a confirmation modal for regression) would reduce the accidental-regression surface.

## Duplicate assignment potential

The `documentation_tasks` table has no unique constraint on `booking_id`. Each time a booking is saved and the dialog is shown, a new task row can be inserted for the same booking. Rapid double-submit, browser back/forward, or re-opening an already-booked entry can produce duplicates. A unique index on `booking_id` (if one task per booking) or `(booking_id, assigned_to)` (if one per assignee) would enforce the invariant at the database level.
