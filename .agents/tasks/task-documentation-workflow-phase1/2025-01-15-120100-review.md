# Documentation workflow: tasks table, assignment, and dashboard (v2)

This change introduces a `documentation_tasks` table with a 9-stage enum, a post-booking "Assign to Documentation" dialog, and a purpose-built documentation dashboard with stats, time filters, search, and forward-only stage progression. RLS enforces admin-sees-all / assigned-user-sees-own for SELECT, admin/sales/bd for INSERT, admin/assigned for UPDATE, and admin-only DELETE. A unique index on `booking_id` prevents duplicates.

All four issues from the v1 review have been addressed: the overly broad SELECT policy clause was removed, the stage dropdown now restricts to current-and-forward stages, null `bookingUuid` surfaces a warning toast and skips the dialog, and a unique index on `booking_id` guards against duplicates.

Watch for: forward-only stage enforcement is client-side only — a direct Supabase call can regress a task's stage without restriction (**confirmed**); the `stageMutation.isPending` flag is shared across all rows so clicking one stage dropdown disables all others simultaneously (**confirmed**).

**Verdict**: APPROVED

## High-level view

Stage transitions are enforced forward-only in the UI via a filtered dropdown, but the database UPDATE policy has no constraint on stage ordering. Any authenticated user who passes the RLS check (admin or assigned user) can set the stage to any value via a direct API call. Whether this matters depends on threat model — for an internal CRM with trusted users this is low risk, but it's worth documenting as a known gap for future hardening.

The stage mutation uses a single `useMutation` hook shared across all table rows. While `isPending` is true (one row's stage is being saved), the `disabled` prop fires on every row's dropdown simultaneously. For a small team this is a minor UX annoyance rather than a blocker, but it means rapid stage changes across multiple tasks are serialized by the UI even though the backend could handle them concurrently.

## Client-only stage ordering

The dropdown filters stages to only show the current and subsequent positions:

```tsx
{DOC_STAGES.filter((_, idx) => idx >= DOC_STAGES.findIndex((s) => s.id === task.stage)).map((s) => (
  <SelectItem key={s.id} value={s.id}>{s.label}</SelectItem>
))}
```

This prevents accidental backward transitions in the UI. However the mutation itself is:

```tsx
const { error } = await supabase
  .from("documentation_tasks")
  .update({ stage })
  .eq("id", taskId);
```

No server-side constraint validates that the new stage ordinal is ≥ the current one. The RLS UPDATE policy only checks identity (`is_admin OR assigned_to = auth.uid()`), not stage direction. A Postgres trigger that compares the enum ordinals of `OLD.stage` and `NEW.stage` would close this gap:

```sql
CREATE FUNCTION enforce_stage_forward()
RETURNS trigger AS $$
BEGIN
  IF NEW.stage::text < OLD.stage::text THEN  -- enum comparison by ordinal
    RAISE EXCEPTION 'Stage regression not allowed';
  END IF;
  RETURN NEW;
END;
$$ LANGUAGE plpgsql;
```

For an internal tool with a small team, the UI-only enforcement is likely sufficient for Phase 1. The concern is informational — flag for Phase 2 if audit requirements emerge.

## Shared mutation pending state across rows

The `stageMutation` is a single `useMutation` instance. When it fires for task A, `stageMutation.isPending` becomes `true` globally, and every row's `<Select disabled={stageMutation.isPending}>` locks out interaction:

```tsx
<Select
  value={task.stage}
  onValueChange={(v) => stageMutation.mutate({ taskId: task.id, stage: v as DocStage })}
  disabled={stageMutation.isPending}
>
```

A straightforward fix is to track the currently-mutating task ID in component state and only disable that row's dropdown:

```tsx
const [mutatingId, setMutatingId] = useState<string | null>(null);
// in mutationFn: setMutatingId(taskId) before, clear onSettled
// in Select: disabled={mutatingId === task.id}
```

This is cosmetic for small task lists but becomes a real friction point once the dashboard has 20+ rows.
