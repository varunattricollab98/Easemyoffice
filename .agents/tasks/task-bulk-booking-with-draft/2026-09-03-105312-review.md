# Bulk booking queue + draft crash-safety — review pass v3 (final fix verification)

Commit `c376d22` resolves the v2 blocker: a batch booking whose DB insert succeeds but whose Google Sheet append fails (`res.sheet.ok === false`) now has its just-inserted DB row deleted before the batch stops, so the id it briefly consumed is genuinely released rather than left dangling for the next save to collide with. The rollback runs before `scheduleBalanceReminders`, the entry is dropped from `succeeded` and re-queued, and the requeue is rebuilt as `[...failedForms, stopForm, ...remaining]` so the rolled-back stop entry survives for a clean retry. Toast wording now reports the retry count and names earlier hard failures. The change stays entirely within `handleSaveAll`; the single-booking mutation, `persistBooking`, and the restore effect are untouched.

The v2 cross-save duplicate-id defect is eliminated: after a sheet failure the failed booking is neither in the DB (row deleted) nor consuming a sheet id (append never landed), so `getNextBookingIdFromSheet` — which scans the sheet — hands the same id back cleanly on retry with no second row to collide against. The requeue invariant holds across all four current-form positions, and reminders are now scheduled only for fully-saved bookings. The prior-pass fixes (#1 double-persist, #3 restore-on-open) are intact.

Watch for: (1) **possible** — if the rollback `delete` itself errors (network/RLS), the orphan DB row lingers with a sheet-unused id and the v2 cross-save collision resurfaces on the next save; this is surfaced in the toast (`rollbackNote`) rather than silently swallowed, so it is a visible degraded path, not a hidden defect. No blocking concern remains.

**Verdict**: APPROVED

## High-level view

The rollback closes the last correctness gap. On a soft sheet failure the loop deletes the inserted row via `supabase.from("bookings").delete().eq("id", res.bookingUuid)` (guarded on a non-null uuid), records nothing in `succeeded`, and breaks. Because the id was never appended to the sheet and its DB row is now gone, the sheet-scanning id resolver sees the id as free and reissues it on retry against no competing row — the distinct-id guarantee is restored across saves, not just within a batch.

The requeue rebuild is `[...failedForms, stopForm, ...remaining]`, and the live-form reset condition flipped to `includeCurrent && !currentNotAttempted`. Traced across the four positions the current form can occupy (it is the stop entry / after the stop / a prior hard-error / a prior success), every entry lands in exactly one place — queue XOR live form — with no loss and no double-persist. `retryCount = failed.length + 1 + remaining.length` matches the rebuilt queue length exactly.

Reminders now schedule only on the DB-plus-sheet success path, so a rolled-back booking leaves no reminder rows pointing at a deleted uuid.

The one residual is the rollback delete failing, which re-opens the v2 collision for that entry — but it is reported to the user through `rollbackNote` in the toast, so it is a visible best-effort degradation rather than a silent regression.

### Rollback eliminates the cross-save collision

The v2 hard-stop saved the failing booking's DB row and merely stopped the loop, which moved the duplicate-id collision from "iteration i+1" to "the next save." `c376d22` deletes that row:

```ts
if (!res.sheet.ok) {
  if (res.bookingUuid) {
    const { error: delErr } = await supabase.from("bookings").delete().eq("id", res.bookingUuid);
    if (delErr) {
      rollbackNote = ` (warning: could not roll back the saved row for ${form.client_name || "the failed booking"}: ${delErr.message})`;
    }
  }
  sheetAllOk = false;
  sheetSyncStopIndex = i;
  break;
}
```

`getNextBookingIdFromSheet()` derives the next id by scanning the sheet's booking-id column, never the DB. On a sheet-append failure the row was never appended, so after the delete the id is unused in both stores and no persisted row carries it. A retry (drain the queue, or a later single save) resolves that same id and inserts against no competitor — one row, one id. The v1/v2 distinct-id acceptance criterion now holds across saves, not only within a batch. The delete is guarded on `res.bookingUuid` being non-null, so a booking that failed before returning a uuid is not blindly deleted.

### Requeue invariant across the four current-form positions

`toPersist` is `[...queue, currentForm?]`, so the current form (when included) is always the last index. `notAttempted = toPersist.slice(sheetSyncStopIndex + 1)`; `currentNotAttempted = includeCurrent && currentIndex > sheetSyncStopIndex`; `remaining = currentNotAttempted ? notAttempted.slice(0, -1) : notAttempted`.

```ts
const failedForms = failed.map((ff) => toPersist[ff.index]);
const stopForm = toPersist[sheetSyncStopIndex];
setQueue([...failedForms, stopForm, ...remaining]);
if (includeCurrent && !currentNotAttempted) resetForm();
```

- Current form **is** the stop entry (`currentIndex === sheetSyncStopIndex`): rolled back, captured as `stopForm` in the queue, `currentNotAttempted` false → form reset. In queue once, live form cleared.
- Current form **after** the stop (`currentIndex > sheetSyncStopIndex`, not attempted): `currentNotAttempted` true, `remaining` drops its trailing element (the current form), form left live. In live form once, not queued.
- Current form is a **prior hard-error**: it would have to be the last index with a stop at a later index, which is impossible — the last index has nothing after it. So a failed current form co-occurring with a later stop cannot arise; when the current form is itself the stop, it is handled by the first case.
- **Prior successes**: dropped from the queue (never added to `failedForms`, `stopForm`, or the after-stop `remaining` slice).

`failedForms` (indices strictly below the stop) and `remaining` (indices strictly above) are disjoint, and `stopForm` is the single index between them, so the three lists partition without overlap. `retryCount = failed.length + 1 + remaining.length` equals the new queue length, so the toast count is accurate.

### Reminders scheduled only for fully-saved bookings

`scheduleBalanceReminders(form, res.bookingId, res.bookingUuid)` moved below the `!res.sheet.ok` block and after `succeeded.push`, so it runs only on the DB-plus-sheet success path. A rolled-back stop entry — whose DB row is deleted — never schedules reminders, so no reminder rows reference a deleted booking uuid.

### Rollback-failure residual

If the `delete()` returns an error, the orphan row stays and the entry is still re-queued and reported as not saved. On retry the sheet reissues the same id, and the lingering orphan row now shares it — the v2 collision for that single entry. This is the only path that reproduces the defect, it requires the rollback itself to fail, and it is surfaced to the user via `rollbackNote` appended to the toast rather than hidden. A hard guarantee would need a DB unique constraint on `external_booking_id` or id reservation ahead of the append; absent that, the surfaced best-effort rollback is a reasonable shipping posture and not a blocker.

### Single-path parity and type consistency

`c376d22` touches only `handleSaveAll`. The single-booking `mutationFn`/`onSuccess`, `persistBooking`, `scheduleBalanceReminders`, the ack-email/doc-assign dialogs, and the restore/save/clear draft effects are unchanged, so the classic single-save flow and the v2 restore-on-open fix (#3) behave as before. New locals (`rollbackNote: string`, `stopForm: BookingForm`) are consistently typed; `res.bookingUuid` is `string | null` and the delete is guarded on it. Accepted prior dispositions stand: the resolved id is not written back to the live form (#4) and the batch omits per-booking ack-email/doc-assign (#5, a documented product decision) — neither is a correctness defect. CI remains the authoritative tsc/build gate (sandbox is integrations-only).
