# Bulk booking queue + draft crash-safety — review pass v2 (fix verification)

Commit `f8eb3b2` addresses the three blocking issues from pass v1: the current-form double-persist on partial failure (#1), the mid-batch duplicate `external_booking_id` on a soft sheet-sync failure (#2), and the restore toast firing on page load (#3). #4 and #5 were dispositioned as accepted (form-id write-back left to `res.bookingId`; batch ack-email/doc-assign omitted by design) and remain so. All changes stay within `src/components/dashboard/new-booking-dialog.tsx`; the single-booking mutation and its `onSuccess` were not touched and behave as before.

#1 and #3 are correctly and completely fixed. #2's within-batch behavior is now correct — the loop hard-stops on `res.sheet.ok === false` before fetching the next id, and the requeue math retains succeeded / hard-failed / not-attempted / current-form entries each in exactly one place with no loss and no double-persist. But the hard stop leaves a **residual duplicate-id defect at the retry boundary**: the stop entry's DB row is saved with an id that was never appended to the sheet, so the next booking created (retry or otherwise) is handed that same id.

Watch for: (1) **confirmed** — the hard-stop entry is saved to the DB with an `external_booking_id` whose sheet row never landed, and `getNextBookingIdFromSheet()` derives the next id by scanning the sheet, so the next booking created reuses that id → two DB rows share one `external_booking_id`. The fix moves the collision from within-batch to the next-save boundary rather than eliminating it. (2) **possible** — the hard-stop toast reports saved count and not-attempted count but never mentions bookings that hard-errored earlier in the same batch, even though they are silently re-queued.

**Verdict**: NEEDS_CHANGES

## High-level view

The restore effect now early-returns when `!open` and depends on `[draftKey, open]`, so restore and its toast fire on first dialog open instead of on page mount, still at most once per key. This also gates the save effect: because `restoredKeyRef.current` is only set inside the restore effect, the save effect's `restoredKeyRef.current !== draftKey` guard now means a draft is only written after the dialog has been opened once. That is acceptable — the form can only be filled from inside the open dialog (`isFormFilled` ignores the auto-populated `sales_agent`), so nothing worth persisting can exist before the first open, and crash-safety for the realistic flow is preserved.

The plain partial-failure branch now resets the live form whenever `includeCurrent`, regardless of whether the current form succeeded, closing the #1 double-persist: a failed current form lives only in the requeued `failedForms`, never also in the live form.

The batch loop treats `res.sheet.ok === false` as a hard stop: the booking's DB row is recorded as saved, the loop breaks, not-yet-attempted entries stay queued (with the current form excluded from the requeue when it is among them, so it stays live), the draft is kept, and an explanatory error toast is shown. Within a single batch this guarantees distinct ids. The unresolved gap is across saves: the stop entry's id was never marked used in the sheet, so the very next `getNextBookingIdFromSheet()` returns it again and the next booking collides with the already-persisted stop entry.

### Hard stop closes the within-batch collision but not the cross-save one

The loop now breaks on a soft sheet failure before the next id fetch:

```ts
scheduleBalanceReminders(form, res.bookingId, res.bookingUuid);
if (!res.sheet.ok) {
  sheetAllOk = false;
  sheetSyncStopIndex = i;
  break;
}
```

Within the batch this is airtight: no further `getNextBookingIdFromSheet()` runs, so no second booking can be minted against the unused id. The problem is that the stop entry is still pushed to `succeeded` and reported as saved, and its DB row carries `bookingId`. `getNextBookingIdFromSheet()` resolves the next id purely by scanning the sheet's bookings column (`readSheetConfig("bookingid")` in `bookings-sheet.ts`), never the DB. Because the stop entry's row never reached the sheet, the sheet still lists that id as unused. The next save — whether the user hits "Save all" again to drain the queue, or later creates a single booking — fetches the same id and inserts a second `bookings` row with it. There is no unique constraint on `external_booking_id` in this insert path, so both rows persist. The v1 acceptance criterion (each booking gets a distinct id) is still violated; the failure has just moved from "iteration i+1 within the batch" to "the next save after the batch." Making the stop entry's id genuinely unused (roll back its DB row on sheet failure, or requeue it rather than mark it saved) or reserving the id before the append would close it.

### Requeue math is otherwise sound

For the hard-stop branch the queue is rebuilt as `[...failedForms, ...remaining]`:

```ts
const currentNotAttempted = includeCurrent && currentIndex > sheetSyncStopIndex;
const remaining = currentNotAttempted ? notAttempted.slice(0, -1) : notAttempted;
const failedForms = failed.map((ff) => toPersist[ff.index]);
setQueue([...failedForms, ...remaining]);
if (includeCurrent && currentIndex <= sheetSyncStopIndex) resetForm();
```

The current form is always the last index of `toPersist`, so only two cases arise: it is the stop entry (`currentIndex === sheetSyncStopIndex`), in which case it is saved, dropped from `remaining` because it is not in the after-stop slice, and the form is reset; or it is after the stop (`currentIndex > sheetSyncStopIndex`), in which case `remaining` drops its trailing entry and the form is left live, so it is queued nowhere and persisted nowhere-yet — it stays exactly once, in the live form. `failedForms` (indices strictly below the stop) and `remaining` (indices strictly above) are disjoint, so nothing is duplicated or lost across the two lists. The one rough edge is messaging, not correctness: those re-queued hard failures are invisible in the hard-stop toast.

### Current-form double-persist (#1) closed

The plain partial-failure branch now resets on inclusion, not on success:

```ts
const failedForms = failed.map((ff) => toPersist[ff.index]);
setQueue(failedForms);
if (includeCurrent) resetForm();
```

A current form that failed is captured in `failedForms` (its index maps into `toPersist`) and the live form is cleared, so the next "Save all" rebuilds `toPersist` from the queue alone and the booking is attempted once. Content is preserved in the queue whether it succeeded or failed.

### Restore-on-open and the save-effect gating (#3)

The restore effect early-returns while closed and re-runs on open:

```ts
useEffect(() => {
  if (!open) return;
  if (restoredKeyRef.current === draftKey) return;
  restoredKeyRef.current = draftKey;
  ...
  toast("Restored your saved booking draft");
}, [draftKey, open]);
```

The toast now surfaces when the user opens the dialog rather than on page mount, and the once-per-key ref still prevents repeats. The knock-on effect is that the save effect — guarded by `if (restoredKeyRef.current !== draftKey) return;` — no longer arms until the dialog has been opened once, since the ref is set only here. This is safe: `isFormFilled` keys off user-entered fields and deliberately excludes the auto-populated `sales_agent`, so a closed, never-opened dialog has an empty form and empty queue, nothing worth persisting exists before the first open, and the write path can't be reached with meaningful data until after the ref is set. Crash-safety for the real editing flow (open → type → refresh) is intact.

### Type consistency and single-path parity

The new locals (`sheetSyncStopIndex: number`, `notAttempted`/`remaining`/`failedForms: BookingForm[]`) are consistently typed; `toPersist.slice(...)` yields `BookingForm[]`, and `sheetAllOk` is still read in the full-success branch so it is not a dead binding. Nothing in `f8eb3b2` touches the single-booking `mutationFn`/`onSuccess`, `persistBooking`, or the ack/doc dialogs, so the classic flow is unchanged. CI remains the authoritative tsc/build gate (sandbox is integrations-only).
