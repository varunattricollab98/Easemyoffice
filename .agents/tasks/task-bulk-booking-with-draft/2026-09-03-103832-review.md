# Bulk booking queue + localStorage draft crash-safety for the New Booking dialog — review pass v1

Adds two capabilities to `NewBookingDialog`, entirely within `src/components/dashboard/new-booking-dialog.tsx`: an "Add another booking" queue that stages validated forms and a "Save all (N)" button that persists the queue plus the current form sequentially, and a per-user localStorage draft so an in-progress form and its queue survive a refresh until the user discards them or a save fully succeeds. The refactor pulls the per-booking DB insert + sheet sync into a shared `persistBooking(form)`, factors the money math into a pure `deriveBooking(form)` used by both the live render and both save paths, and extracts `scheduleBalanceReminders(...)` so the single and batch paths schedule reminders identically. The single-booking flow is delegated to `persistBooking` and keeps its ack-email / doc-assign dialogs.

Watch for: (1) **confirmed** — on a partial "Save all" failure where the *current form* is the entry that failed, it is pushed into the queue but the live form is not cleared, so the next "Save all" persists that booking twice (two DB rows, two ids). (2) **likely** — `syncBookingToSheet` fails soft (returns `{ok:false}`, never throws), so a mid-batch sheet-append failure does not mark the id used, and the next iteration fetches the *same* id — two DB rows share one `external_booking_id`, violating the distinct-id guarantee. (3) **confirmed** — the "Restored your saved booking draft" toast fires on page load (the dialog is always mounted), not when the dialog opens.

**Verdict**: NEEDS_CHANGES

## High-level view

The queue is ordinary component state (`BookingForm[]`); "Add another booking" validates the live form with the same predicate that gates Save, deep-copies it in, resets the form, and fetches a fresh fallback id. "Save all" builds `[...queue, currentForm?]` and runs a strictly sequential `for` loop over `persistBooking`, which is the design linchpin for id uniqueness: `getNextBookingIdFromSheet` only marks an id used once its row lands in the sheet, and `persistBooking` awaits `syncBookingToSheet` before returning, so a sequential loop hands out distinct sequential ids — as long as every sheet append actually succeeds.

That last qualifier is the batch's soft spot. The sheet sync is best-effort by design and returns `{ok:false}` rather than throwing, so the loop treats a failed append as success and the next id fetch collides with the just-used id. In the single-booking flow this was harmless (one booking); in a batch it produces duplicate `external_booking_id`s.

Partial-failure handling keeps failed entries in the queue, drops succeeded ones, and keeps the draft — correct in spirit, but the current-form-as-last-index case has a double-persist bug when the current form itself fails.

The draft layer is namespaced per user (`emo:new-booking-draft:<user.id>`), versioned `{v:1,form,queue}`, written debounced and guarded, and restored through a shape-tolerant `mergeForm` that can't crash on a stale shape. Restore is gated to run once per key but not to the dialog being open, so its toast surfaces on page load. Clear-on-success is wired into every single-save terminal branch and full-batch success; cancel and partial failure correctly leave the draft intact.

The single-booking behavior is otherwise preserved: same column mapping, same sheet `values` array, same ack-email and doc-assign dialogs, and reminders reproduced field-for-field through the shared helper.

1. **Double-persist of a failed current form** — on partial "Save all" failure, if the current form (last index) failed, it is added to the requeued `failedForms` but the live form is not reset, so it exists in both the queue and the form; the next "Save all" saves it twice. Clear the form whenever it was included, regardless of success, or exclude the current entry from `failedForms` and leave it only in the live form.

3. **Restore toast fires on page load, not on dialog open** — the restore effect keys on `draftKey` and the dialog is always mounted, so "Restored your saved booking draft" shows before the user opens the form. Gate restore/toast on `open` (or only toast on first open).

### Sequential id resolution and the soft-failure hole

The uniqueness guarantee rests on `persistBooking` awaiting `syncBookingToSheet` before returning and the batch running a plain sequential `for` loop (no `Promise.all`). Both hold: `getNextBookingIdFromSheet()` is called directly (not through the react-query `booking-next-id` cache), so each iteration hits the edge function fresh and sees the prior iteration's appended row.

The hole is that "append succeeded" is never actually required. `syncBookingToSheet` returns `{ ok: false, note }` on a failed or timed-out append and throws on nothing:

```ts
const sheet = await syncBookingToSheet(values);
return { sheet, bookingId, bookingUuid: insertedBooking?.id ?? null };
```

`persistBooking` returns normally, the loop records the booking as succeeded (`succeeded.push`), and only tracks `sheetAllOk` for the toast wording. But if that append failed, the sheet still lists the id as unused, so the next iteration's `getNextBookingIdFromSheet()` returns the same id. The DB inserts both rows (no unique constraint enforced here), so two bookings ship with one `external_booking_id`. The acceptance criterion "each booking receives a DISTINCT, sequential external_booking_id … because syncBookingToSheet is awaited" is only met on the happy path; the await guarantees *ordering*, not *success*. Recommend treating `res.sheet.ok === false` as a batch failure for that entry (leave it in the queue, don't advance to the next id) so a broken sheet connection can't mint duplicates.

### Partial-failure requeue and the current-form double-save

```ts
const failedForms = failed.map((ff) => toPersist[ff.index]);
setQueue(failedForms);
const currentIndex = includeCurrent ? toPersist.length - 1 : -1;
const currentSucceeded = includeCurrent && !failed.some((ff) => ff.index === currentIndex);
if (currentSucceeded) resetForm();
```

`toPersist` is `[...queue, currentForm?]`, so the current form (when included) is the last index. On partial failure the failed entries — including the current form if *it* failed — are written into the queue via `setQueue(failedForms)`. But the live form is reset only when the current form *succeeded*. So when the current form is the one that failed, the same booking now lives in two places: the queue (as a failed entry) and the live form (untouched). The next "Save all" rebuilds `toPersist = [...queue, currentForm]` and persists it twice — two DB rows, two ids consumed. Fix by resetting the form whenever `includeCurrent` (its state is preserved in the queue either way), or by keeping a failed current form only in the live form and excluding it from `failedForms`.

### Draft restore runs on mount, not on open

The dialog (`<Dialog open={open}>`) is always mounted; `open` only toggles visibility. The restore effect depends on `[draftKey]` and runs as soon as the user id resolves:

```ts
useEffect(() => {
  if (restoredKeyRef.current === draftKey) return;
  restoredKeyRef.current = draftKey;
  ...
  toast("Restored your saved booking draft");
}, [draftKey]);
```

So on any page where this component is rendered, a returning user sees the "Restored…" toast (and `setF`/`setQueue` run) before they ever open the New Booking dialog. Crash-safety still works, but the toast is misplaced. Gating restore on `open` — or only toasting the first time the dialog opens with a restored draft — matches the intent. The save effect writing while closed is harmless because it's gated by `isFormFilled`/non-empty queue.

### Shape-tolerant restore

`mergeForm` starts from `initialForm`, copies over only keys present in `initialForm` and only when the stored value is a string, and coerces `payment_type` back to `"full"` unless it is exactly `"partial"`, so a stale/partial/extra-field payload can't inject unknown keys or crash the form. `JSON.parse` plus the `v === 1` check are inside try/catch, and queue entries pass through the same merge — the guarded-parse and stale-shape criteria hold.

### Single-path parity and the un-synced id field

`mutationFn: () => persistBooking(f)` and `onSuccess` uses `res.bookingId` for `savedBookingData`, the ack dialog, and reminders, so persisted data and the email use the resolved id. The one behavioral drop versus the old code: the old `mutationFn` did `setF((s) => ({ ...s, booking_id: fresh.nextBookingId }))` after resolving, so the visible Booking ID field updated; `persistBooking` no longer touches form state. Since the form is reset on every terminal branch this rarely shows, but between a resolve-at-save and the reset the provenance field can still read the `EMO-BK-*` fallback. Confirm acceptable.

### Batch omits ack-email and doc-assign by design

The batch loop only calls `scheduleBalanceReminders` per booking and shows one summary toast; it deliberately does not open the per-booking ack-email or doc-assign dialogs (documented inline as avoiding N stacked modals). Defensible UX, but a real functional gap: bookings created via "Save all" never send an acknowledgment email and never get a documentation assignment, unlike single saves. Product should confirm that batch-created bookings don't need those, or the flow needs a batched equivalent (e.g., a single post-batch assignment step).
