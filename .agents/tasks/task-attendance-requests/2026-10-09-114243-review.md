# Employee attendance requests — WFH, absence clarification, missed-login regularization (v1)

Employees can now raise three kinds of attendance request to the admin from My Attendance: plan/report a work-from-home day (or range), explain an absent day, or supply the login/logout times for a day they forgot to punch. It extends the existing HRMS request machinery rather than forking it — a new `attendance_requests` table modeled on `leave_requests`, three new actions on the `hr-requests` edge function, and new cards on My Attendance and the admin Approvals screen. The on-approval effects reuse the attendance row's existing `remote_*` columns for WFH and run missed-login corrections through the same pure day-closing rules a normal punch uses, so a corrected day scores identically to one punched live. The pending-count badge on the HRMS nav now folds in the new queue.

Watch for: the admin-only decision path and the no-write-policy table are the trust boundary — both hold up (confirmed). The migration is manual and the My-Attendance request card throws (not degrades) if the owner hasn't applied it yet (confirmed). The WFH "minimal row" is anchored at IST midnight with zero worked/window minutes, which is correct for the month count but shows as a 12:00 AM login in the Today card (possible, cosmetic).

**Verdict**: APPROVED

## High-level view

The write model is the security story. `attendance_requests` carries RLS with a SELECT policy (admin or own-via `employees.profile_id`) and no INSERT/UPDATE/DELETE policy at all; the edge function running as service role is the only writer. Every employee action resolves the employee from `profile_id` server-side and never trusts a client-supplied employee id or status field, and the decision action is gated on an `admin` role lookup. An employee cannot approve their own request or inject a decision field through a crafted body.

The approval effects are deliberately routed through the shared pure rules. A missed-login approval recomputes the attendance row with the same `regularizedAttendance`/`closeDay` path the logout flow uses, so worked-minutes, window-minutes, lateness and status stay consistent with a normally-punched day, and the status it writes is always one the attendance CHECK constraint allows. WFH approval reuses the `remote_*` columns, converging a reactive-WFH row or creating a minimal remote-approved row for a planned/absent day. Absence clarification mutates no attendance — the approved request is the record.

The two copies of the rules file (browser and edge `_shared`) are byte-identical and a test enforces it. IST handling round-trips exactly: `requested_login_at`/`requested_logout_at` are built at a fixed +05:30 offset from the work date and read back the same way.

The migration is applied manually by the owner and is fully idempotent. The app mostly degrades gracefully when the table is absent — the admin pending-count tolerates the error — but the employee's request-history query throws on error, so that one card renders a failed state until the migration lands.

### No-write-policy table + server-resolved identity

The migration gives `attendance_requests` a single SELECT policy — `is_admin(auth.uid())` OR `employee_id IN (SELECT id FROM employees WHERE profile_id = auth.uid())` — and deliberately no INSERT/UPDATE/DELETE policy, mirroring `leave_requests` and `attendance`. With RLS enabled and no write policy, authenticated clients cannot write the table at all; the `hr-requests` function writing as service role is the only path in.

That function never trusts the caller for identity or decision state. On an employee action it looks the employee up by `profile_id` from the authenticated user and bails if there is none; the insert row is assembled from a fixed whitelist (`employee_id` from that lookup, `type`, normalized dates, reason, and the two timestamps), so `status`, `decided_by`, `decided_at`, and `admin_note` can never be set from the request body. `decide_attendance_request` is guarded by an `admin` membership check in `user_roles` before it will flip status, and both cancel and decide re-assert the row is still `pending` in the UPDATE's own `.eq("status","pending")` filter, so a double-decide or cancel-after-decide is a no-op rather than a clobber. An employee cannot self-approve or forge a decision.

### Missed-login correction through the shared close-day rules

```
decide_attendance_request(approve) ─ type=missed_login ─▶ regularizeDay
    minutesSinceIstMidnight(login/logout)  ─▶ regularizedAttendance (shared)
        istMidnight + minutes ─▶ ISO instants
        minutesBetween / windowMinutes / lateMinutes / closeDay
    patch: first_login_at,last_logout_at,worked,window,is_late,late,status,overtime,schedule_*
```

The status this path writes is always `present`/`short`/`half_day` — all allowed by the attendance status CHECK; `in_progress` only arises mid-session, which the correction never produces, so the recompute cannot violate the constraint. The function requires both a login and a logout and skips the row if either is missing, matching the validator's rejection of a one-sided pair. It snapshots the schedule from the existing row when present (same precedence as attendance-punch) else from `hr_settings` by weekday, so a correction uses the day's real policy rather than a default.

### WFH approval reuses the remote_* columns

`approveRemoteDay` updates an existing attendance row (so a reactive-WFH day — the employee logged in from home and the row already exists in `remote_status=pending` — converges to approved) or inserts a minimal row for a planned/absent day. The minimal insert sets `first_login_at` to IST midnight (the column is NOT NULL) and `status: "present"`, with `work_mode: remote`, `remote_status: approved`. In `summarizeMonth` a remote-approved row with a settled status is counted as a present remote day, which matches the existing test for approved WFH. Two consequences worth confirming rather than fixing: the row contributes zero credited minutes (`window_minutes`/`worked_minutes` default to 0), so an approved-ahead WFH day with no real punch adds a present day but no hours to the month total; and the midnight `first_login_at` renders as "12:00 AM" in the Today card's login stat if that day happens to be today. Neither affects the present/absent accounting the feature is about.

The range loop for a multi-day WFH approval is capped at 366 iterations, matching the validator's own range handling, so a malformed `from/to` cannot spin.

### Duplicate / overlap guards and lenient attendance sanity checks

Apply-time guarding is per-type: the clash query blocks a pending-or-approved request of the *same* type whose `[from_date,to_date]` overlaps the new one. WFH is treated as a range; the other two are forced single-day by the validator. Filing both an absence clarification and a missed-login for the same day is allowed by design (different types for different remedies). On top of that, missed-login is refused when the day already has a completed (logged-out, non-in-progress) record — nothing to fix — and absence clarification is refused when the day already has any `first_login_at`. These are intentionally lenient (only block on a clear contradiction), which keeps odd-but-legitimate cases unstuck.

### IST round-trip and the HH:MM contract

`requested_login_at`/`requested_logout_at` are stored by `istInstant(date, minutes)` (fixed +05:30 from IST midnight) and read back by `minutesSinceIstMidnight`, which invert exactly — verified for 09:30 → `…T04:00:00Z` → 570. The browser sends login/logout from an `<input type="time">`, i.e. `"HH:MM"`, and the server's `parseHHMM` matches `^(\d{1,2}):(\d{2})` and range-checks the result, so the UI output and server parser agree. The validator and the UI's `canSubmit` both enforce logout-after-login, so the client-side disable and the server rejection stay in sync.

### Degradation when the migration is not yet applied

The migration is manual and idempotent (every object guarded by IF NOT EXISTS / DROP…CREATE), and nothing in the app assumes it auto-runs. The admin pending badge issues the three count queries with `Promise.all` and sums `?? 0`, so a missing `attendance_requests` table leaves the badge working off the other two. The employee-facing read helper, `fetchAttendanceRequests`, instead throws on any query error, so the "Attendance requests" card on My Attendance will show a failed-query state rather than an empty list in the window before the owner applies the migration. Confirm that window is acceptable, or let the helper treat a missing-relation error as an empty result.

### Test coverage

The 12 new cases exercise real logic and would fail on a revert, not static-assert theatre. `validateAttendanceRequest` is driven across all three types: WFH ahead-planning and range defaulting, reason trimming and the 3-char floor, the backdate boundary (exactly-at vs one-past), the future-date rule (forbidden for the two past-only kinds, allowed for WFH), the ahead-window cap, single-day enforcement for the past-only kinds, and the login/logout pairing (login required, logout-must-be-after). `regularizedAttendance` is checked for a normal on-time flexible day (worked/window/overtime and the exact ISO instants), a late fixed-day login, and the short/half_day thresholds — so the shared-rule path that writes the attendance row is pinned to concrete numbers. The byte-identical guard test reads both copies and asserts equality.

Not tested: the edge-function handlers themselves (Deno, outside Vitest/CI) — `approveRemoteDay`'s update-vs-insert branch, `regularizeDay`'s skip-when-missing-logout, the duplicate/overlap SQL guard, and the admin-only gate are verified by reading only. The `summarizeMonth` treatment of a zero-minute approved-WFH minimal row is covered indirectly by the existing approved-WFH test but not for the specific minimal-row shape this feature inserts.
