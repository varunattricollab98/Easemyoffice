# Center-align stacked email cells to stop leading-emoji detach in payment-ack template

The payment acknowledgment email is an inline-styled, table-based HTML template built in `buildPaymentAckEmailHtml` (with the shared "Your Dedicated Manager" block from `buildEmailSignature`). Leading HTML-entity emoji (🔒 lock, 🎉 party, 👋 wave, 📞 phone, ✉ envelope, etc.) were detaching to the far-left edge instead of sitting inline/centered with their text, most visibly at mobile widths. The change traces this to the `@media (max-width:640px)` rule, which flips grid/stack cells to `display:block; width:100%` and thereby drops the effect of the cells' `align="center"` attribute, left-aligning their content. The fix adds `text-align:center !important` to that stacked-cell rule and adds explicit `text-align:center` onto a handful of emoji-leading blocks in both files (+9/-9, two files).

The media-query rule correctly targets the real cause. But the blanket `!important` center now also applies to card blocks that are intentionally left-aligned on desktop, changing their mobile appearance; and the three inline additions in the white "Hello" section are defensive redundancy rather than fixes for the reported bug.

**Watch for:** the media rule now force-centers *every* `.stack`/`.grid-2/3/4 td` on mobile, including the left-aligned Service Details and Plan/Tenure/Location cards — a deliberate-looking left alignment silently becomes centered on phones (confirmed). Desktop detach for those same left-aligned card emoji is not addressed by this change (likely). Three inline `text-align:center` additions in the white welcome section are no-ops given the parent already centers (confirmed).

**Verdict**: APPROVED

## High-level view

The bug is a mobile-layout regression baked into the responsive rule: collapsing table cells to block-level discards the `align="center"` that centered them on desktop, so emoji-leading content jumped left. Adding `text-align:center !important` to the stacked-cell rule restores centering after the block-collapse and is the correct, email-safe lever. Gmail and Apple Mail honor the media query; Outlook desktop (Word engine) ignores it entirely but also never applies `display:block`, so its desktop table layout with `align="center"` stands unchanged — the fix is inert-but-safe there.

The `!important` center is applied indiscriminately to all stacked cells. The "What Your Payment Covers" cards (📦 Plan, 📅 Tenure, 📍 Location, ⚡ Activation) are left-aligned by design on desktop; on mobile they now center. That may be the intended visual, but it is a behavioral change beyond "stop emoji detaching" and should be an explicit decision, not a side effect. And desktop detach for those same left-aligned card emoji is untouched by this change.

The three inline `text-align:center` additions to the white welcome section (the "Hello {name} 👋" heading and the two green/thank-you banners) sit inside a `<td>` that already declares `text-align:center` and are not `.stack` cells, so neither desktop nor mobile rendering changes. Harmless, but they do not address any detach.

### Outlook robustness caveat

Gmail (mobile app and web), Apple Mail, and iOS Mail process `<style>` media queries and get the corrected centering. Outlook desktop uses the Word rendering engine and ignores `<style>`/media queries entirely — but for the same reason it never applies the `display:block` collapse, so it keeps the desktop table layout where `align="center"` already works. The fix is inert-but-safe on Outlook and corrective on the clients that exhibited the bug. No external CSS, web fonts, or layout primitives were introduced, so the email-safety constraint holds.

### Blanket `!important` center reaches intentionally left-aligned cards

```
.stack, .grid-2 td, .grid-3 td, .grid-4 td { ... text-align:center !important; }
```

This selector matches every stacked cell, not only the emoji-detach cases. The consequential group is the left-aligned-by-design cards: the "What Your Payment Covers" grid — 📦 Plan, 📅 Tenure, 📍 Location(s) Covered, ⚡ Activation Window. On desktop these cards left-align their heading and body text; under the new rule they center on mobile only. That restyles legitimately left-aligned card copy — it may be the desired mobile look, but it is a consequence of the broad selector, not a targeted decision. If the intent was to preserve left alignment for those cards while still centering the emoji, the `!important` blanket does not allow that distinction. Confirm the mobile card alignment is intended.

### Desktop detach for the left-aligned cards is not addressed

The change only alters behavior inside the mobile media query (plus redundant inline centers elsewhere). The Plan/Tenure/Location/Activation card headings — e.g. `<div style="font-weight:800; ...">&#128230; Plan</div>` — carry no `text-align` and sit in a left-aligned card on desktop. If the emoji in those blocks detach on desktop as well (the report emphasizes mobile, but "far-left edge" could apply to both), this change does nothing for them on desktop. Confirm against the original report whether desktop detach in the card grid was in scope; if it was, those blocks need their own handling since they should stay left-aligned (emoji inline with the text, not centered).

### Redundant inline centering in the white welcome section

Three additions in `buildPaymentAckEmailHtml` — the `Hello ${client_name} 👋` heading, the green "family of 5,000+" banner, and the dark-section "Payment secured · Compliance-first · 4.9/5 rated" line — add inline `text-align:center`. All three live inside a `<td style="... text-align:center;">` and are plain block divs (not `.stack`/grid cells), so they already inherit centering on desktop and are never touched by the block-collapse media rule on mobile. They should not be mistaken for the fix — the mobile media-query rule is what actually resolves the reported detach.

### Scope respected

The diff is confined to the two email-template functions. No booking-form logic, save flow, bulk/draft handling, or GST/profit calculation was touched; the hero `LOGO` `<img>` and footer social `<img>` tags are unchanged; edits are additive `text-align` properties appended inside existing inline-style strings, with no template-literal interpolation or backticks disturbed. No email-HTML unit tests exist, so verification is necessarily a human eyeball in Gmail/Outlook/mobile, which repo CI (`tsc --noEmit` + `vite build`) does not cover.
